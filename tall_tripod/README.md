# tall_tripod — トポロジー最適化の検証用モデル

## これは何なのか

**トポロジー最適化がちゃんと働くかを確かめるための、背の高い3脚のモデル**です。
実際に使っている低重心3脚（`../osmo_tripod/`）とは別物で、**印刷して使う部品ではありません**。

`tall_tripod.scad` に「絶対に残す場所」「材料を置いてよい空間」「空けておく場所」を書き、
`tall_tripod_study.json` に「どんな力がかかるか」を書きます。
それを `topopt` に渡すと、**カメラを 20 cm の高さに支えるにはどう材料を置けばいいか**の
答えが形として返ってきます。

## どう動いているのか

上端にカメラを留める**頭部**があります。ここだけは形が決まっています——
相手（DJI Osmo Action 6 のケース）の寸法が決めているからです。

その頭部の周り、**プレートに載る円柱まるごと**を「ここに材料を置いてよい」と宣言します。
下端の床は「ここで接地してよい」とだけ言います。**脚を何本、どこに、どの太さで出すかは
書いていません。** それを決めるのが最適化の仕事です。

使ってよい材料は空間の 4 % だけなので、「どこに置けば一番効くか」を選ばざるを得ない、
という仕掛けです。

## v4 で何を変えたのか（2026-08-06）

**前の版（v3）は、答えの大部分が入力に書いてありました。**

| | v3 | v4 |
|---|---|---|
| 材料を置ける空間 | 円板＋上に細る錐台 | **円柱ひとつ**（Ø240 × 146 mm） |
| 絶対に残す場所 | 頭部＋**接地パッド3つ＋ハブ座** | **頭部だけ** |
| 脚の位置 | **CAD が決めていた**（3点固定） | 最適化が決める |
| 支柱の太さ | 設計空間の外形が決めていた | 最適化が決める |
| カメラ取合いの出力 | 解析マス目に量子化（4 mm） | **CAD から切り直し**、0.5 mm 刻み（`finish` 段） |
| 解析マス目 | 4.0 mm | 10.0 mm（粗い実験用。可変） |

v3 のレポートには「示していないこと」という節があって、そこに
「脚の位置は人間が決めています」と書いてありました。**v4 はその節を減らすための版です。**

### 接地をどう扱っているか

この道具には「**荷重と拘束は preserve（絶対に残す領域）の上にしか置けない**」という規約が
あります。自由な領域に拘束を置くと、最適化がその下の材料を消してしまうからです。
v3 が接地パッドを preserve にしていたのはこの規約のためで、その代償が
「脚の位置を人間が決める」ことでした。

v4 では例外をひとつ足しました。

```json
{"region": "catch_n", "fix": "xyz", "contact": "ground"}
```

`"contact": "ground"` と書いた拘束は、preserve ではなく**設計空間の底面1ボクセル層**に
切り詰められ、さらに**接地面の節点だけ**を固定します。
だから最適化が床に何も置かなければ、その構造は本当に支えを失って、
コンプライアンスが即座に発散します。**規約の目的（拘束の下を消させない）は守ったまま、
場所の指定だけを外した**ことになります。

### ただし、転倒は表現できていません

接地拘束は**両側拘束**です。引っ張っても床から離れません。
つまり**FEA の中でこの部品は転倒できない**——コンプライアンス最小化は転倒を目的に持てません。

これは実測で痛い目を見ました。「片脚引っ掛け」を1方位だけにして回したら、
最適化が出したのは**その方位に傾いた1本柱**でした。接地2点、footprint 50 × 140 mm。
安全率は 128 と出ます。**見た瞬間に倒れる形が、解析上は合格します。**

対処は「片脚引っ掛け」を **120 度ずつ3ケース**にすることです。
構造が3つの扇形すべてに届かないと、どれかのケースで発散します。これで三脚が出ました。

**つまり、人間がまだ決めていることが1つ残っています**——「3方位、だいたいこの辺」。
半径も接地点の数も脚の形も最適化が決めていますが、ゼロではありません。
詳しくは [known-issues G7](../docs/known-issues.md)。

## v5 で何を変えたのか（2026-09-08）

**v4 の結果は部品ではなかった。** 設計空間が頭部を丸ごと包んでいたので、材料は頭部の
側面や上面にも回り込みました。仕上げ（`finish`）は CAD の頭部を足し戻していましたが、
解析した 10 mm ボクセルの頭部はそのまま残していたので、出荷ファイルは
**30 mm の角ブロックの中に 19 mm の頭部が埋もれた形**でした。平滑版はもっと悪く、
10 mm グリッドに σ=1 ボクセルのガウスをかけると脚が消え、頭部は団子になりました。

v5 は 2 つを変えました。

| | v4 | v5 |
|---|---|---|
| 頭部に材料を繋いでよい場所 | 全面 | **台座の底面だけ**（`attach`。他の面には 1 ボクセルの非接触殻） |
| 仕上げの頭部 | 解析ボクセル＋CAD（重ね） | **解析ボクセルを捨てて CAD に置き換え**（触れていた 1 ボクセルは橋として残す） |
| 平滑化 | 密度場全体に σ=1 ボクセル | **最適化した材料だけ**、細グリッド上で σ=解析ボクセルの半分。CAD・接地層は固定、体積は一致させる（v6 で σ=1 ボクセルに変更） |
| 試し回しのマス目 | 10 mm | **4 mm**（`--voxel 4`。10 mm では台座の底が 1〜2 セルで丸めが答えを決める） |

探索（4 mm・80 反復・`--quick`・GPU）：最適化 406 秒。抽出後の `finish` は
154,036 三角形の等値面で**水密・1 ボディ・自己交差なし**、平滑化による体積変化 0.00 %。
最適化した材料は頭部の直下 256 mm²（4×4 セル）だけで繋がり、頭部の他の面には触れていません。
v4 の成果物は `archive/v4_before_attach_2026-09-08/`、この 4 mm 探索 run は
`archive/v5_quick_4mm_2026-09-08/` に残してあります。

### 採用した run（3 mm・`--quick` なし、2026-09-09）

```bash
# 1) 最適化から出荷形状・スライスまで（CalculiX 段はブロック STL で落ちる。下の 2) で回す）
python -m topopt run tall_tripod/tall_tripod_study.json --model tall_tripod \
    --voxel 3 --iters 80 --converge

# 2) 平滑化後の形を CalculiX で再解析（3 段階メッシュ収束つき）
python -m topopt ccx tall_tripod/03_optimization/tall_tripod_study_t40_smooth.stl \
    --study tall_tripod/tall_tripod_study.json --out tall_tripod/03_optimization \
    --mesh-mm 7 --converge

# 3) ccx の結果を報告書に取り込む
python -m topopt run tall_tripod/tall_tripod_study.json --model tall_tripod \
    --only report,publish
```

格子 84×84×54（自由セル 244,032）、最適化 1,146 秒。形は上面視 120° の 3 本脚が
中央の 1 本柱にまとまる三脚で、最適化した材料は**台座底の attach 面 324 mm²（36 セル）を
使い切って**頭部に繋がり、頭部の他の面には触れていません。しきい値 0.40 を採用、
体積 297,459 mm³・質量 377.6 g、スライスは 6 時間 26 分・188.8 g
（うちサポート 59.2 g = 31.4 %）。

**CalculiX の再解析は平滑 STL に対して行いました。** `topopt run` の ccx 段は `extract` が
出すブロック状 STL を渡すので、そのままでは非多様体稜線 36 本で Gmsh が体積メッシュを
張れません（`--repair` は tall_tripod で体積 21 % 喪失の前科があるので使っていません）。
平滑 STL（16,100 三角形・水密・1 ボディ）は素直に通り、14 / 7 / 3.5 mm の 3 段階で
**6 ケース × 3 段階すべて PASS**。支配ケース LC3se は SF p99.5 268.5 → 296.9 → 308.1、
最大変位 0.0223 → 0.0230 → 0.0224 mm、荷重と反力の釣合い誤差は全ケース 0.000 %。

**それでもメッシュ収束は `pass: false` です。** 変位変化 3.3 %→2.9 %、応力変化
4.8 %→2.6 % と数値は許容 5 % に収まったのに、**応力ホットスポットが 17.5 mm 動きました**
（許容 7 mm）。3 段階とも位置は接地面（z = 0）の上で、支配ケースでは
[27.0, −25.5, 0] ↔ [36.0, −10.5, 0] と**同じ接地パッチの縁を行き来しています**。
これは「ただし、転倒は表現できていません」の節で書いた**接地拘束が両側拘束（糊付け）である
ことの帰結**で、細かくするほど特異点が鋭くなります——最悪要素の安全率も LC3se で
47.7 → 47.8 → 12.3 と単調に落ちます（それでも要求 1.50 の 8 倍）。`--exclude-mm` は
最悪要素の判定からしか除外しないのでこの検査は通りません。直すには study 側
（接地パッドを preserve にする等）の変更が要ります。

**解像度検査（最薄部 2 セル）は 3 mm でも落ちます。** 4 mm で `8.00*`、3 mm で `6.00*`——
`*` はツール自身が付ける「グリッド律速、構造の値ではない」の印で、**床は格子に張り付いて
一緒に下がります**。`--voxel 2` にしても同じ床（`4.00*`）を追いかけるだけなので、ここは
`design.filter_mm`（現在 20 mm）のノブです。一方**代表断面は実寸として収束しつつあります**
——16.97 mm が 4 mm で 4.0 要素、3 mm で **5.7 要素**。

**残った 3 つの FAIL と、それぞれのノブ:**

| FAIL | 何が起きたか | 触るところ |
|---|---|---|
| 密度場が収束していない | 80 反復を使い切って停止（shape change 4e-3、`tol_change` 0.002 に未達） | `--iters` を増やす |
| メッシュ収束 | 上の接地特異点 | study（接地の与え方） |
| 自己支持 | 1 ボクセル・9 mm² が 45° 円錐の外（4 mm 版の 1 ボクセル・16 mm² から縮小） | `design.overhang` |

## v6 で何を変えたのか（2026-09-09）— **実物が組めなかった**

**報告：「触るなと言った部品（最初に置いた頭部）まで平滑化される。**
**そしてこの部品には Osmo Action 6 の防水ケースが取り付けられない。」**

出荷 STL を測ったら、原因は2つあり、どちらも**図では見えないもの**でした。

### 1. ナットポケットが袋穴だった — これが「ネジで固定できない」の正体

締結は M5 の蝶ネジ（ノブ）＋ナットです。ナットは**外側から押し込む**ので、
ポケットの口が開いていなければ入りません。

v5 はナット側の進入路（Ø18 × 16 mm）を `obstacle`（＝最適化が材料を置かない場所）
にだけ書いていました。宣言は効いていて、最適化はそこに材料を置いていません。
**それでもナットは入りませんでした**——**obstacle は preserve を退けないから**です。

台座（preserve）は爪より X に広い形です。

| 高さ | 台座の半幅 | 爪の外面 |
|---|---|---|
| z = 136（台座の上面） | 11.30 | 11.00 |
| z = 132 | 11.87 | 11.00 |
| z = 128 | 12.44 | 11.00 |

つまりポケットの口（x = 11.0）は**台座の肉の中**にありました。
出荷 STL で口を横切る 3,228 本のラインを数えると、**758 本が塞がっていました。**

`osmo_tripod.scad`（実際に使っている低重心3脚）の `knob_clearance()` は
**最初から両側を切っています**。検証モデルのほうが片側を落としていた、という話です。

**直し方：逃がしは `obstacle` と `finish.cut` の両方に書く。**
`mount_cuts()` に `screw_access()`（ノブ側＋ナット側）を入れました。
そのうえで、次に落とすための assert を5本足しています——
「進入路がナットポケットより太いか」「進入路が台座の外まで届いているか」
「ノブの逃がしが台座の外まで届いているか」など、**すべて数値で書ける条件**です。

### 2. 平滑化が CAD の面を 0.34 mm 外へ動かしていた

v5 の finish 段は「CAD のセルを 1 に固定」していました。これで守れるのは
**CAD が削られない**ことだけで、**CAD が外へ動く**ことは止めていません——
ガウスは CAD ボディを含んだマスクにかかっていたので、頭部は自分自身をぼかし、
等値面は CAD 面の外側に出ます。

| | CAD | v5 出荷 | v6 出荷 |
|---|---|---|---|
| ナット側の爪の外面 | x = 11.00 | **11.34** | 12.25（v6 の CAD どおり） |
| 丸め落ちた CAD 頭部 | — | **322 mm³** | — |

**この 0.34 mm が 1 の膜になってポケットを塞いでいました。**
（ポケットは公称面ちょうどで終わっていたので、面が外へ動いたぶんが残る。）

直したのはツール側（`topopt/finish.py`）です。**CAD ボディはガウスに入れず、
「占有率」として合流させます**——各セルを CAD がどれだけ埋めているかを
細分割サンプリング（既定 3×3×3）で出し、その 0.5 が CAD 面なので、
体積一致で選んだしきい値に `+ (level − 0.5)` で載せ替える。
こうすると**しきい値がいくつでも等値面は CAD 面に乗ります**。穴（`cut`）も同じ扱いです。

精度は 2 つに分かれました。**引用するときに混ぜないこと。**

| 何に効くか | いくつか |
|---|---|
| `feature_tolerance_mm` = finish ボクセル 1 つ（1.00 mm） | ボクセル版 `_finish_voxel.stl`、最適化した本体 |
| `smooth.cad_tolerance_mm` = finish ボクセル / サンプル数（0.33 mm） | 出荷する等値面の **CAD 面** |

実測（v6 出荷 STL を 0.125 mm で測る）：爪 4.00 / 2.00 / 7.00 mm、溝 4.25 mm——
**すべて CAD の値そのもの**。面の位置は三角形の頂点で見て CAD と 0.06 mm 差。

### 3. それでも「かくかくしている」— 平滑化が半分だった

上の 2 つを直したあと、**「何も変わっていないように見える」「最適化した部品はスムーズに
してほしい」**と返ってきました。**絵にして初めて分かりました。**

平滑化の既定 `auto` は「解析ボクセルの半分」（3 mm グリッドなら σ=1.5 mm）でした。
これでは**階段が消えず、階段を丸めた瘤が数珠つなぎになります**——解析セル1つにつき瘤1つ。
数字の上では「軸方向の平らな面は面積の 10 %」で階段には見えないのに、目には明らかに凸凹です。

`auto` を**解析ボクセル1つ**（σ=3.0 mm）にしました。瘤は消え、殻は水密・1ボディのまま、
体積も一致（±0.00 %）。1.5 ボクセルはそれ以上滑らかにならず、殻検査が open edge と呼ぶ
継ぎ目が出ます。**CAD の頭部は σ を変えても 1 ミクロンも動きません**——ガウスに入っていないので。

そして**表面の絵を出すようにしました**：`04_print/preview_print.png` が
**出荷する STL そのもの**の陰影図（3方向、フラットシェーディング）。
それまで run が出す図は全部「解析グリッド上の場」の絵で、**表面を映したものが1枚も
ありませんでした**。「かくかくしている」は場の統計では見えません。

**`04_print/` から `*_smooth.stl` を外しました。** あれは粗い密度場**全体**へのガウスで、
**preserve ごと丸めます**（爪が団子になり、ナットポケットは閉じます）。
`03_optimization/` には残してあります——`topopt ccx` が再解析するのはこれです——が、
「印刷するもの」のフォルダに `smooth` と付いた別ファイルがあると、そちらが良い版だと
読まれてしまいます。

### 4. 底面のギザギザと、接続の浮き

さらに3点の指摘。**「底面がスムーズ化されていない」「部品と最適化部品の接続が浮いている」
「接続する箇所だけスムーズにしてつなげないか」。** 原因は別々でした。

**底面。** 接地層は「脚が浮かないように」セルごとに 1 で固定していました。固定していたのは
**解析グリッドの footprint そのもの**なので、上の本体だけが丸まり、
**滑らかなドームが 1 mm 厚のギザギザのスカートの上に立つ**形になっていました。
接地面は材料の終わりではなく**切断面**なので、畳み込みの前にプレートの下へ材料を**鏡像**して
対称にしました。断面は削れも太りもせず、輪郭は本体と同じに丸まり、浮きもしません。

**接続。** 2つ重なっていました。(a) CAD をぼかしから外した副作用で、最適化材料**自身**のぼけが
CAD 面に近づくほど落ちるため、支柱が着地の直前で細る。(b) `attach` は繋いでよい面以外に
1 ボクセルの非接触殻を張るので、**台座（30 × 30 mm）が attach 面（18 × 18 mm）より広いぶんは
必ず宙に浮く**——実測で**全周 2.00 mm の隙間**でした。

(a) は「**接続する箇所だけ**両方のボディを含むぼかしに寄せる」で直しました（ご提案どおりです）。
重みは最適化材料自身のぼけ値なので、自分の表面で 1、2σ で 0 ——連続で、距離計算も要りません。
(b) は `finish.bridge_mm`（既定＝解析ボクセル1つ＝殻の厚み）で、**フィレットが非接触殻の中に
入ってよい**ことにしました。

| | v6 | v7 |
|---|---|---|
| 台座の下の隙間（x = 10 / 12 / 14 mm） | 2.00 / 2.00 / 2.00 mm | **0 / 0 / 0** |
| 接合部に足した材料 | — | 1,170 mm³ |

**ただし最初の版は効かせすぎでした。** ブレンドの場所を重みの減衰だけで決めていたので、
2σ の全方向に効いて**台座の周りにぐるりと襟**が育ち、「**部品の下にクッションがついていて、
それと最適化部分がくっついている**」形になりました。**効かせてよい範囲は集合で書く**もので、
いまは「**両方のボディから `bridge_mm` 以内**」＝両者が出会う入隅だけに限っています。
枕は消え、隙間は 0 のまま、取合いも接地面も変わりません（`*_raw.stl` と並べて描くと一目です）。

**埋めてよいのは殻だけです。** 利用者が宣言した obstacle（カメラの首振り、ノブを回す空間）には
入りません。`cut` の周りにも入りません——フィレットは CAD 面の**外**に足す材料なので、
公称面ちょうどで終わる穴はそれに塞がれるからです（#91 の膜が別経路で戻る）。
**解析はこのフィレットを見ていません。** 足したぶんは `info.smooth.bridge_mm3` に出ます。

**おまけ：閉じているはずの殻に 3 本の穴が開いていました。** STL は角を float32 で持ち、
100 mm 付近の刻みは約 8e-6 mm。同じ点が別の float32 に落ちて辺が相手を失っていました
（44.4 万辺のうち 3 本）。書き出す前にセルの 1e-4（0.1 µm）へ量子化して直しました。

### 5. すきまを広げた（頼まれたから。ただし原因ではなかった）

「もっと余裕をもって」に対して、**噛み合う面の合計あそびを 1.0 mm 以上**にしました。

| | v5 図面 | v5 出荷（実測） | v6 |
|---|---|---|---|
| 中央爪（ケースの 3.00 の隙間に入る） | 2.40 | **2.00** | 2.00（あそび 1.00） |
| メス溝（ケースの 3.00 の爪が入る） | 3.80 | **4.00** | 4.25（あそび 1.25） |
| 溝の半径（爪の外接 7.50 に対して） | 8.50 | — | 9.00 |
| ボルト穴（ピボット Ø5.00） | Ø5.60 | Ø5.60 | Ø5.80 |

**正直に書いておきます：v5 の出荷ファイルは図面より既に緩かった**（2.00 / 4.00）。
だから「すきまが足りなくて嵌まらなかった」possibility は低く、
**嵌まらなかった主因はナットポケットのほう**だと考えています。
すきまは、頼まれたことと、FFF には図面 0.30 が薄いことの両方を理由に広げました。

### 6. ナットポケットの床が 1.80 mm しかなかった

`osmo_tripod.scad` には `assert(nut_floor >= 2.5, "締めると割れる")` があり、
tall_tripod には**その assert がありませんでした**。床＝ナットが締め付けで押す壁です。
`fin_nut_t` 6.00 → 7.00 で 2.80 mm。**兄弟モデルの assert は、写すか、無い理由を書く。**

これでナット側の爪が x = 12.25 まで伸びるので、台座の上面も 11.3 → 12.3 に広げました。
**台座の底（15 × 15）は動かしていません**——そこが `attach` の面で、
動かすと最適化の入力が変わるからです。

### 最適化は回し直していない（回すのは判断の問題）

**密度場は v5 のままです。** 変わったのは preserve が 3 mm セルで 16 個増えたこと
（+432 mm³、全部が頭部）だけで、候補の FEA は新しい形で回し直しました。

| | v5 | v6 | なぜ |
|---|---|---|---|
| しきい値 0.40 の体積 | 297,459 mm³ | 297,891 mm³ | preserve が 16 セル増えた（16 × 27 = 432） |
| 安全率 p99.5（voxel 3 mm） | 217.7 | 215.8 | 同じ 16 セルが分位に入った |
| 最悪要素の安全率 | 49.13 | 49.13 | 支配位置は接地面で、頭部ではない |
| 最大変位 | 0.024 mm | 0.024 mm | 同上 |
| スライス | 6h26m・188.8 g | 6h25m53s・188.89 g | ほぼ同じ |

**頭部は preserve で、最適化は一度も触っていません。** 3 mm の FEA は頭部を分解できないので、
ここを 0.2 mm 動かしても解は変わりません——だから density は回し直していません。
**回し直すかどうかは設計者の判断です**（`--voxel 3 --iters 80` で約 20 分）。
回すなら study の `regions.mount_head` などの x 範囲も v6 の頭部に合わせてください
（いまは v5 の範囲のままで、v6 頭部の部分集合になっています）。

`topopt compare` も回しました（`03_optimization/cmp_v6/`）。ただし**この数字は
そのまま読めません**——`compare` は保存済みの 2 値化（しきい値 0.5）を「最適解」として使い、
`--level` を無視します。出荷する形はしきい値 0.40 ＋ CAD 頭部なので、比べているのは
別のしきい値の 2 つの形です（質量差 +5.1 % がそれ）。LC4t の「2.58 倍」も
コンプライアンス 0.00 対 0.01 の比で、表示桁の下です。**平滑化した形そのものの評価は
`topopt ccx` のほう**（下の「CalculiX 再解析」）を見てください。

`03_optimization/ccx_summary.json` は v5 の平滑 STL に対する再解析のままです。
平滑 STL は最適化した本体だけの形（取合いは入っていない）なので、
**同じ本体を記述している**とみなしていますが、v6 で回し直したものではありません。

## v7 で何を変えたのか（2026-09-10）— **カメラ固定部を別部品に差し替えた**

**依頼：「`dji_osmo_action6_mount.stl` を追加したので三脚のカメラ固定部分に差し替えて。**
**トポロジー最適化の再実行はいらないはず。」**

差し替えたのは、この三脚が自前で描いていた頭部（3枚爪＋ヒンジ＋台座、21 × 19 × 36 mm）を、
**子機用に設計された DJI Osmo Action 6 の固定部品**（`mechanical/parts/child/exterior/
printed/dji_osmo_action6_mount/`、104 × 79.45 × **84.5** mm）に、丸ごと置き換えたことです。

**性格がまったく違う部品です。** 旧頭部はケースをヒンジで挟んで ±30° 傾けるもの。
新しいほうは**傾きません**——ケースの背面を板に当て、前側の2か所で受けて姿勢を決め、
純正ねじを 3 枚爪に通して締結します。だから study の `obstacle`（カメラの首振り空間）は
**もう存在しない機械を描いています**。それでもそのまま残してあるのは、
**記録済みの最適化の入力だから**です（変えると密度場と突き合わなくなる）。

### どう置いたか — 基準はねじ軸

マウント側の座標系は三脚と同じ（+Y がカメラ前、X がねじ軸、Z が上＝造形方向）なので、
置き換えは**平行移動 1 回**です。マウントのねじ軸は自身の底面から 24.0 mm 上。
この三脚の `z_hinge` は 136 mm で、**カメラ高さも転倒計算も全部その数字で書かれている**ので、
軸のほうを合わせて **+112 mm** 動かしました（`02_setup/place_camera_mount.py`）。

底板の下面は z = 112、最適化が繋いでよいと言われた台座下面は z = 110。
この 2 mm は部品の隙間ではありません——finish 段が、解析した頭部のボクセルを捨てるときに
**最適化材料と接していた 1 ボクセル（z = 111..114）を橋として残す**ので、
底板はその中に立ちます。`attach` が空けていた 2 mm と同じもので、`bridge_mm` は元々その寸法です。

### 一体化か、ボルト留めか

マウントの底板には **M5 4 本・22 × 32 mm ピッチの貫通穴**があり、本来はボルト留めの部品です。
**利用者の選択は「一体化（1 部品に union）」**でした。したがって穴は使いません
（CAD にあるので形としては残っています）。代償は造形で、下の表のとおりサポートが増えます。

### ネジまわりのクリアランス

締結は M5 の蝶ネジ（ノブ）＋ナットです。効くものが3つあって、性格が違います。

| | 何のためか | v3 | v4 | v6 |
|---|---|---|---|---|
| ナットのポケット | ナットが入るか | 二面幅 8.60 / 深さ 3.20 | **9.00 / 4.20** | 9.00 / 4.20 |
| ポケットの床 | 締めて割れないか | 2.80 | **1.80**（assert 無し） | **2.80**（assert あり） |
| ノブの逃げ | **指が入って回せるか** | 片側 0.75 / 深さ 12 | **1.50 / 16** | 1.50 / 16 |
| ナット側の進入路 | レンチ・指が届くか | **無し** | Ø18 × 16（obstacle のみ） | **obstacle ＋ cut** |

**ノブの逃げと進入路は「部品の穴」ではなく「部品の外の空き空間」です。**
v3 では設計空間が頭部より下で終わっていたので埋めようがありませんでしたが、
v4 は頭部の周り全部が設計空間になったので、**obstacle として宣言しないと埋められます**。

**そして obstacle だけでは足りません（v6 で判明）。** obstacle が退けるのは
最適化が置く材料だけで、**preserve（台座）は退けません**。台座は爪より X に広いので、
ナット側は obstacle に書いてあっても台座に塞がれた袋穴のままでした。
逃がしは **`finish.cut` にも書く**——上の「v6 で何を変えたのか」を参照。

### 本当に組めるか確かめた

寸法表の照合と、組んでみることは別の証拠です。STEP をそのまま STL に起こして、
±30 度を5点掃いて干渉を見ました。

```bash
python -m topopt step2stl osmo-action-6.step /tmp/case.stl
python -m topopt clearance tall_tripod/02_setup/tall_mount_finished.stl /tmp/case.stl \
    --hinge-z 136 --case-drop 11 --angles -30,-15,0,15,30
```

**5点すべて干渉ゼロ、最接近 0.50 mm**（v6。v5 は 0.30 mm）。
掃引だけでは「ナットが入るか」は分かりません——それは別に測ります
（ポケットの口を横切るラインのうち、外向きに材料が残っているものを数える）。

## 粗いマス目でも取合いが消えない仕組み（`finish` 段）

10 mm のマス目でカメラ爪（2.40 mm）は表現できません。**マス目より細かいからです。**
これは以前「粗いマス目が使えない理由」でした。いまは違います。

**頭部は preserve で、最適化は一度も触っていません。** CAD として入ったものが、
解析グリッドから出てくる必要はありません。だから出荷する形はこう作られます。

1. 最適化の結果を細かいグリッドに**そのまま**（整数倍で複製、ずらさない）
2. 解析した頭部のボクセルを**捨てる**（`add` が preserve と同名なので置き換え。
   最適化した材料が触れていた 1 ボクセルだけ橋として残す）
3. CAD の頭部を**足す**
4. 最適化した材料だけを**丸める**（頭部・接地層は固定、obstacle には出ない、体積は一致させる）
5. CAD の穴（爪の溝・ボルト穴・ナットポケット・ノブの逃げ）を**引く**

引くのが最後なのは順序の問題ではなく正しさの問題です。先に引くと足し戻しで埋まり、
丸める前に引くとガウスが埋めます。

### ただし「CAD の寸法どおり」ではありません

刻みが**解析ボクセルから finish ボクセルに変わる**だけです。出荷ファイルを 0.1 mm で
測り直すとこうなります。

| 部位 | CAD | 出荷ファイル（v5 まで） | 10 mm グリッドだけなら |
|---|---|---|---|
| 外側の爪（ノブ側） | 4.00 mm | 4.00 mm | 存在しない |
| 溝 | 3.80 mm | **4.00 mm** | 存在しない |
| 中央爪 | 2.40 mm | **2.00 mm** | 存在しない |
| ボルト穴 | Ø5.60 mm | Ø5.60 mm | 存在しない |

**幅は finish ボクセル1つぶんまで狂います。** 両側の面が独立に丸まり、
しかも cut は外側に丸まる（セル中心が穴に入れば消える）ためです。

**v6 (2026-09-09) でここが変わりました。** CAD ボディは「セルを埋めている割合」
として合流するようになったので、**面はセルの境界に貼り付かなくなりました**。
同じ測り方（0.125 mm）で v6 の出荷ファイルを測ると：

| 部位 | CAD | 出荷ファイル（v6） |
|---|---|---|
| 外側の爪（ノブ側） | 4.00 mm | **4.00 mm** |
| 溝 | 4.25 mm | **4.25 mm** |
| 中央爪 | 2.00 mm | **2.00 mm** |
| 外側の爪（ナット側） | 7.00 mm | **7.00 mm** |

**引用する数字が 2 つに分かれたことに注意してください。**
`feature_tolerance_mm`（finish ボクセル 1 つ）は**ボクセル版と最適化した本体**に、
`smooth.cad_tolerance_mm`（finish ボクセル ÷ サンプル数）は**出荷する等値面の CAD 面**に
効きます。どちらも図面値ではありません。

この程度なら**組めます**（爪が細い＝すきまが増える方向、溝が広い＝同じく緩む方向）が、
**締まりばめには使えません**。細かくするのはメモリ律速で、0.5 mm でもこの部品全体で
1億1900万セルです。

**そして FEA が見たのは粗いほうの取合いです。** 頭部まわりの応力は 10 mm 以上の
分解能を持ちません。最適化された本体も**解析グリッドのまま**で、0.5 mm に再サンプルしても
情報は増えません。**本体から取合い寸法を取らないこと。** [known-issues G8](../docs/known-issues.md)。

## マス目を変えるときは、値段を先に聞く

`topopt setup` は、グリッドを作ったあと**実際に1回 FEA を解いて**、
指定した反復数ぶんの所要を出します。式で外挿しません——記録済み run 6本は
セルあたりコストが2倍以上ばらついていて、セル数だけでは説明できないからです。

```bash
python -m topopt setup tall_tripod/tall_tripod_study.json --out /tmp/chk --voxel 5 --iters 80
# → runtime  80 iterations x 6 case(s) ~ ...  (range ... ; one cold solve took ... s)
```

| マス目 | 領域のセル数 | 80反復 × 6ケースの実測／見積 |
|---|---|---|
| 10.0 mm | 6,720 | **16.8 分（実測）**／見積 5 分 |
| 5.0 mm | 52,000 | 未実施 |
| 3.0 mm | 244,000 | 未実施 |

出荷 STL を**解き直す**ほうは別物です（要素数がずっと少ない）。実測：

| マス目 | 要素数 | LC1f | LC3se | 6ケース合計 |
|---|---|---|---|---|
| 5.0 mm | 2,480 | 3.0 s | 8.7 s | — |
| 3.0 mm | 11,549 | 41.3 s | 70.9 s | **3 分 49 秒** |
| 2.0 mm | 38,651 | 208 s | 244 s | 約 25 分 |

見積は「1回の冷えた solve × ケース数 × 反復数」で、実測はその 0.5〜1.5 倍に入ります
（校正表は `topopt/src/topopt/runtime.py`）。

## 使い方

すべてリポジトリ直下から。

```bash
# 1. 形を作り直す（.scad を編集したとき）
SCAD="/c/Program Files/OpenSCAD/openscad.exe"
for p in preserve design_space obstacle mount_solid mount_cuts mount_finished reference; do
  "$SCAD" -o tall_tripod/02_setup/tall_$p.stl -D "part=\"$p\"" tall_tripod/tall_tripod.scad
done

# 2. 設定が正しいかを見る。**必ず PNG を見ること。所要時間もここで出る**
python -m topopt setup tall_tripod/tall_tripod_study.json --out tall_tripod/02_setup

# 3. 最適化から報告・印刷用フォルダまで一括
python -m topopt run tall_tripod/tall_tripod_study.json --model tall_tripod --iters 80

# マス目を変える（study の voxel_mm を上書き）
python -m topopt run tall_tripod/tall_tripod_study.json --model tall_tripod --voxel 5 --iters 80
```

**1時間を超える run は切り離して起動する**（`CLAUDE.md` の `Start-Process` の型）。
重い run は1本ずつ（[known-issues G5](../docs/known-issues.md)）。

## 印刷範囲は、解く前に確定している

**設計空間がプリンターより大きければ、最適化が何を出しても印刷できません。**
これは解いたあとに分かることではなく、モデルを描いた時点で分かることです。

同じ検査を二か所に置いてあります。`tall_tripod.scad` は assert で**CAD を描いた時点**で落ち、
`topopt setup` は実際にボクセル化した bounding box で**解く前**に落ちます。

v3 まで、この assert は**脚先端の半径 `r_foot` を見ていました**。設計空間の外形が
たまたま脚先端と同じだったので通っていただけで、**設計空間そのものは一度も
検査されていませんでした**。v4 で脚が無くなるとその偶然も消えるので、
いまは設計空間の外形を直接見ています。

飛ばして 3.6 時間を捨てた実例が [`archive/v1_unprintable/`](archive/v1_unprintable/) にあります。

## 回した結果（2026-08-06）— v4

`topopt run --model tall_tripod --iters 80`、10 mm ボクセル、6,720 セル
（自由 6,668 ／ preserve 12 ／ obstacle 40）、6 荷重ケース、**全体で 10.6 分**。
出荷候補は**しきい値 0.40**、体積 309,000 mm³（うち preserve 12,000 mm³）。

**三脚が出ました。** 上から見ると 120 度に開いた3本脚、横から見ると末広がりの A 字。
接地は**5パッド・3,000 mm²**、footprint 200 × 170 mm。

**この形は人間が描いたものではありません**——が、「3本」だけは人間が言っています。
片脚引っ掛けのケースを 120 度ずつ3つ置いたのは設計者で、
**幅を要求している唯一のケースがそれ**だからです（上の「転倒は表現できていません」）。
最適化が決めたのは、脚の半径・太さ・断面・接地点の数（5つ）・上への繋がり方で、
**脚が3本であることは決めていません**。

| 荷重ケース | 安全率 p99.5 | 最大変位 |
|---|---|---|
| LC1f 横に 1.0 N | 3470 | 0.001 mm |
| LC2 5G の落下 | 771 | 0.003 mm |
| LC3n 北脚を引っ掛けて吊る | 148 | 0.016 mm |
| LC3sw 南西脚 | 122 | 0.025 mm |
| **LC3se 南東脚（支配）** | **12.9** | **0.375 mm** |
| LC4t ねじり | 1904 | 0.001 mm |

判定は **FAIL 2 / UNKNOWN 3 / PASS 9**。

### v3 から良くなったこと

- **取合い面へのサポート着地が 1,552 mm² → 0。** v3 で「造形方向を変えるしかない」と
  書いていた項目が、設計空間を変えたら消えました
- **カメラ取合いが出荷ファイルに入っている。** 10 mm ボクセルなのに 2.40 mm の中央爪が
  あります（`finish` 段）
- **`assumptions.md` の「示していないこと」から、脚の位置が消えました**

### まだ落ちている2つ

**1. 収束していません。** 80 反復で `max_iterations`。v3 と同じで、
密度変化が閾値を一度も下回りません（[known-issues G6](../docs/known-issues.md)）。

**2. 最も薄い断面が 3 要素に届きません。** 20.00 mm ＝ ちょうど 2 ボクセルで、
これは**グリッドの下限そのもの**です。構造の値ではありません。
10 mm では原理的にこれ以上細かくなりません。**マス目を細かくする以外に手はありません。**

### 割り切りと限界

- **10 mm は形を見るための解像度です。** 部材寸法を読まないでください
- **強度が余りきっています**（支配ケースでも 12.9）。設計が良いのではなく、
  転倒律速で荷重を大きくできないから（[known-issues G3](../docs/known-issues.md)）
- **転倒は解析していません。** 接地拘束は転倒を表現できないので、閉形式で別に見ます。
  `tall_tripod.scad` が出すのは「脚を設計空間の縁いっぱいに出したとき」＝
  **最良の場合の上限 1.025 N** だけ。実際の接地半径は run サマリの `ground_contact` を読むこと
- **材料の数値はまだ実測ではありません。** PLA の直交異方性カードは文献の傾向から
  保守側に置いた暫定値です。**絶対値ではなく「どの向きに印刷すべきか」の比較に使ってください**
- **まだ実物を作って測っていません。**
- **出荷 STL を 3 mm で解き直すと、安全率が支配ケースで 7.5 倍違います。**
  同じ形なのに、最適化時（10 mm）が SF 12.9、解き直し（3 mm）が SF 96.4。
  **どちらも「最薄断面 2 要素」で収束していないので、どちらが正しいかは言えません。**
  3分49秒で終わるので、収束スタディは回せます（[known-issues G9](../docs/known-issues.md)）。
  **2026-09-08 に CalculiX（独立ソルバ・8 mm 殻）でも解き直したところ、支配ケース
  LC3se は SF 135 と、また別の値になりました**（下の「CalculiX 再解析」参照）。
  三者三様の数字が並んでいるのは、**どれも収束していないメッシュ同士を比べているから**です

## CalculiX 再解析（2026-09-08）

出荷 STL（`tall_tripod_study_t40.stl`、しきい値 0.40、309セル）を Gmsh + CalculiX で
解き直しました。手順は2段階です。

**1. つまみを塞いでから抽出し直す。** 309セルの STL には非多様体稜線が3本ありました
（セル同士が稜線・頂点だけで接する「つまみ」——ボクセル FEA はそこを共有節点で繋いで
荷重を通しますが、STL ベースの経路はそれを構造として認めません）。`--repair`
（MeshFix）でそのまま修復すると、どのオプションでも**体積の21%（309,000 → 242,833 mm³）
を切り捨てました**。代わりに `generative.heal_pinches` で稜線・頂点接触ごとに橋渡しの
1セルを埋め（積層方向の低い側を選び、obstacle には置かない）、しきい値0.40で再抽出すると
**312セルの閉じた殻**になりました。ファイルは
[`03_optimization/reanalysis/`](03_optimization/reanalysis/)。

**2. 8 mm 殻で CalculiX を回す。** 18,616節点・9,526要素、質量386.88 g。
6ケース全て PASS、釣合い誤差0.0、接地面606節点・3,000 mm²。

| 荷重ケース | 安全率 p99.5（8 mm CalculiX） | 最大変位 |
|---|---|---|
| LC1f 横に1.0 N | 2897 | 0.0011 mm |
| LC2 5G の落下 | 697 | 0.0038 mm |
| LC3n 北脚を引っ掛けて吊る | 285 | 0.0171 mm |
| LC3sw 南西脚 | 199 | 0.0311 mm |
| **LC3se 南東脚（支配）** | **135** | **0.0425 mm** |
| LC4t ねじり | 1536 | — |

最小座屈係数は512（LC3se）。立位ケースの固有振動数は591 / 736 / 844 Hz。
ファイルは [`03_optimization/reanalysis/ccx_8mm/`](03_optimization/reanalysis/ccx_8mm/)。

**同じ形を10 mmボクセル FEA と比べると、6ケース中1ケースしか変位が15%以内に収まらず、
比は1.09〜1.65でした**——10 mmの六面体格子は、1〜3セルしかない細い部材には硬すぎます。
上の「まだ落ちている」節の SF 12.9（10 mm 最適化時）・96.4（3 mm 解き直し）・
135（8 mm CalculiX）は**3つとも別々に未収束のメッシュ**の値なので、どれが正しいかは
まだ決まっていません（[known-issues A3・A6](../docs/known-issues.md)）。

## 10 mm と CalculiX のずれは解像度（2026-09-08）

同じ再抽出形状を 2.5 mm の voxel で解き直すと（`03_optimization/reanalysis/fea_2p5mm/`、2.3 秒）、
片脚ケースは CalculiX 8 mm と 1〜11% で一致した（LC3se 0.0421 対 0.0425 mm）。10 mm の 1.4〜1.6 倍は
グリッドの粗さで、CalculiX 経路の問題ではない（known-issues G10）。

## Phase 6 比較：材料モデルと造形方向（2026-09-08）

同じ study を等方材料・X 造形・Y 造形に書き換えて回した（`archive/phase6_2026-09-08/README.md` に表）。
等方モデルは形をほぼ変えず数字だけ 2 倍硬く見せ（最大変位 0.0345 → 0.0162 mm）、造形方向は形そのものを
変える（接地パッド Z 6 個・X 3 個・Y 1 個、Y 造形の片脚ケースは安全率 37）。サポート体積は
Z 341,000・Y 713,000・X 1,382,000 mm³ で、立てて印刷するのが最小。床を Z に固定したまま `build_axis` を
変えるために `ground_axis` を足した。

## この検証で何を見るか

仕様 [docs/spec.md](../docs/spec.md) §5.1 が挙げている確認項目：

- 離れた接地点と中央のマウントを、最適化が**つないでくれるか** → 通った
- 曲げ・圧縮・ねじり・片脚荷重を**同時に**扱えるか → 通った（6ケース）
- 平たい板ではなく、**立体的な荷重経路**を作れるか → 通った
- **造形方向によって層間の安全率が変わることを検出できるか**
  （`build_axis` を Z / X / Y に変えて3回回し、比べる）→ **未実施**
- この大きさで、要素数・計算時間・メモリが現実的か → 10 mm なら 10 分
- **出てきた形が実際に印刷できるか** → 解く前に検査している

結果は `03_optimization/report.md` を読んでください。判定・失敗した条件・
検査していない条件が、その順に並んでいます。

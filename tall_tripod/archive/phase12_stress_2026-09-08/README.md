# Phase 12：応力制約を tall_tripod で回した（2026-09-08）

`03_optimization/` の記録（10 mm・80 反復・OC・応力制約なし）と**同じ study** に
`design.stress: true` を足して回したもの。**印刷するものではない。**
spec §24 の「応力制約は tall_tripod でまだ回していない」を閉じるための run。

| フォルダ | 変えたもの | それ以外 |
|---|---|---|
| `run/` | `"stress": true`（要求安全率は §15.1 どおりケースごと：通常 3.0／異常 1.5） | 同じ |
| `control/` | **対照**。`"stress": false` ＋ `"optimizer": "mma"` | 同じ |

**対照を足した理由。** 応力制約を有効にすると optimizer が OC から MMA に自動で切り替わる。
さらに記録済みの `03_optimization/` は 2026-08-06 の run で、**自己支持拘束が入る前**
（`settings.overhang` が `null`）。つまり `03_optimization/` と直接比べると、
差が「応力制約のせい」なのか「OC→MMA のせい」なのか「1か月ぶんのコードのせい」なのかが
分からない。`control/` は**応力制約だけを外した**同日・同コード・同 optimizer の run で、
これがあって初めて「応力制約が何をしたか」が言える（known-issues E1 の非対称比較を避ける）。

study はこのフォルダ直下（`*_study.json`）に置き、出力は各サブフォルダへ——
**study を `--out` の中に置くと run の要約が同名で上書きする**（lessons-learned #79）。
`02_setup/` への参照は `../../02_setup/` に書き換えてある。

```
python -m topopt run tall_tripod/archive/phase12_stress_2026-09-08/stress_study.json \
    --out tall_tripod/archive/phase12_stress_2026-09-08/run \
    --iters 80 --no-ccx --no-slice --solver cpu:mg
```

`--solver cpu:mg`：GPU は別プロセスが使用中だったので CPU に固定した。
**`cpu:jacobi` ではなく `cpu:mg`** ——マルチグリッド前処理は同じ答えに一桁少ない反復で
届くので（AGENTS.md）、旧前処理を選ぶ理由は記録済み run との突き合わせのときだけ。

## 読み方

- **応力制約は tall_tripod では何もしていない。** 最悪でも SF×FI 0.024——
  要求ラインの **1/40** の余裕で、制約が一度も効いていない。
  対照（`control/`）と比べると体積 292,000 → 291,000 mm³（0.3%）、
  支配ケースの SF p99.5 が 90.50 → 91.01（0.6%）。
  **どちらも known-issues E2 の分解能（5〜6%）より小さい**ので、差として読んではいけない。
  **かかった費用だけが本物**：最適化の所要が 332 → 677 s（約 2.0 倍。
  荷重ケースごとに随伴解が1回増えるので、ほぼ理論どおり）。
- **理由は known-issues G3 そのもの。** この study の荷重は転倒荷重（1.0 N）で決まっていて、
  強度が形を決めていない。安全率が2桁余っている問題に強度制約を足しても、
  制約は最初から満たされていて何も動かない。
  **「応力制約が効くかどうか」を tall_tripod で検証することはできない**——
  検証したければ先に G3（荷重の決め方）を決める必要がある。
  gd_mount（`osmo_tripod`、要求 SF 3.0、LC3x で VIOLATED）はいまも唯一「効いた」実例。
- **`03_optimization/` との 76.2 → 91.0 の差は応力制約ではない。** 対照が 90.5 を出しているので、
  差の出どころは OC→MMA と、自己支持拘束が入ったこと（記録済み run は overhang なし）。
  **記録済み run を対照として使わないこと**——4 週間ぶんのコードの差が混ざる。
- **しきい値に対する頑健さは MMA 側が上。** 記録済み run は 0.40→0.50 で LC3se の
  SF p99.5 が 76 → 13 に落ちる（脚が1本細って千切れかける）。今回の 2 本は
  0.40/0.50/0.60 のどれを取っても 90〜91 でほぼ動かない（`control/` は 0.60 で 24 に落ちる）。
  **選んだしきい値が違う（0.40 と 0.60）のはこのため**で、抽出段は「一番強い連結候補」を選ぶ。
- **自己支持は今回も落ちている**（`run/` 6 ボクセル、`control/` 3 ボクセル）。
  応力制約とは無関係で、smooth min が真の最小より 0.005 高いことによる取りこぼし
  （AGENTS.md の (3)）。`03_optimization/` は自己支持拘束が入る前の run なので比較対象にならない。
- **同じ report.md の中で要求安全率が食い違って見える。** 「stress constraint」の行は
  LC3sw を **required SF 1.50** と書き、「Structural results」の表は同じ LC3sw を
  **normal / 3.00** と書く。**表のほうが間違っている**——
  最終 FEA（`generative.final_fea`）と抽出段が `load_class` を見ていない
  （known-issues **A7**、同日登録）。tall_tripod は安全率が2桁余っているので合否は変わらないが、
  要求が 3.0 と 1.5 の境目にある部品では変わる。
- **これは 10 mm グリッドの比較。** 3 本とも同じグリッドなので相互比較は対称だが、
  絶対値は known-issues G10 のとおり CalculiX より 1.4〜1.65 倍硬い側にずれている。
  メッシュ判定は 3 本とも「2 要素で粗すぎ」で FAIL（G1）。

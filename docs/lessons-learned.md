# この案件で得た知見

> osmo_tripod（DJI Osmo Action 6 用3脚ホルダー）の設計・最適化・造形で実際に踏んだもの。
> **仕様書の規則の多くはここが根拠**なので、規則を緩める前にこれを読む。
> 各項目の末尾に、対応する仕様（[spec.md](spec.md)）の節を示す。

---

## 設計空間モデル

**1. 「非設計領域」を preserve と obstacle に分けると、設定ミスが検証できるようになる。**
まとめて `keep_in` と呼んでいるうちは「守りたい面」と「避けたい空間」が同じ箱に入り、
どちらも `region & grid.solid` で静かにクリップされて消える。分けたうえで
*荷重と拘束は preserve の上にしか置けない* と決めると、
「押している当の相手を最適化が消す」という一番よくある失敗が**設定エラーになる**。
実際 `gd_study.json` を書く途中で、脚パッド r=8@r47 が接地円板（r=52）から 3 mm はみ出していたのが
これで表に出た（旧方式では黙ってクリップされていた）。 → spec §8.1, §10.3

**2. preserve を書き戻す順序が全部を決める。**
フィルタ・射影・対称化・スムージングはどれも密度を下げる向きに働くので、
preserve=1 を先に代入すると次の1行で削られる。旧 `topo_opt.py` は対称化とオーバーハングフィルタが
`keep_in` の**後**に走っていて、40反復かけて取合い面が静かに丸まっていた。 → spec §11.2

**3. 設計空間に取合いを入れ忘れると、出力に取合いが付かない。**
当たり前に見えて一度やった。設計領域を「土台の円板＋台座」で切ったのでカメラを掴む爪が問題に入らず、
最適化結果は取合いの無い土台だった（`gd_study.json`）。直し方は爪を preserve に、
爪に開ける特徴（U溝・ボルト穴・ナットざぐり・ノブ逃がし）を obstacle に入れること（`gd_mount_study.json`）。
**穴を obstacle にしないと最適化が穴を埋める。** → spec §8.1

**4. `volfrac` は自由セルにのみ掛かる。**
全体体積率 = preserve + volfrac ×（自由セル）。現行設計と質量を揃えるならそこから逆算する。 → spec §8.3

## 測り方

**5. 測定対象を混ぜると、無いはずの違反が見える。**
部材寸法を preserve 込みで測っていたため、2.50 mm のカメラ爪が「filter_mm 4.0 違反」として出ていた。
`filter_mm` が支配するのは**自由セルだけ**なので、最適化部材と部品全体は別々に報告する
（median 7.18 mm と 3.21 mm）。 → spec §15.1, §19.3

**6. 最小部材寸法は 2 ボクセルで床打ちする。**
測定したすべての実行が `min_mm` をちょうど 2×voxel と報告した。それはグリッドが決めた値で、
構造の値ではない。フィルタの長さスケールを確認したければ `filter_mm / 3` 未満のボクセルで測り直す。 → spec §15.1

**7. 境界条件は要素より先に疑う。**
自己診断で片持ち梁が理論値より 23% 硬く出たが、原因は要素ではなく
「固定領域をボクセル4列ぶん取っていた」こと。1列にしたら 4.1% に収まった。
**固定した節点はすべて梁を短くする。** → spec §10.3

**8. 質量を決めているのは1ケースだけのことがある。**
4ケース同時最適化の結果、通常ケースは 24 cm³ でも安全率 11〜16 で余りまくり、
LC3x（こじり）だけが 1.05 で限界。現行 40.3 cm³ が LC3x で稼いでいるのは 1.05 → 1.95 で、
どちらも要求 3.0 に届いていない（＝追加の 16 cm³ は「合格」を買っていない）。
**「どのケースが金を払わせているか」「その金で合格を買えているか」は、全ケース同時に回して初めて分かる。** → spec §10.2

## 最適化の限界

**9. インフィルを最適化に入れても最適形状は変わらない。**
compliance は `1/E` に比例するので、`E` を一様に下げても最適な密度分布は厳密に同一で、
報告値が定数倍されるだけ。形状を変えうるのは密度ではなく**異方性**（`E_z ≠ E_xy`）で、
そこは等方 hex8 要素では表現できていない。積層方向は最終 FEA の破壊指標（層間引張・層面せん断）
には入っているので、**報告している安全率は Z 積層前提の値**。 → spec §2.2, §11.5, §12.2

**10. 最適化の生結果は部品ではない。**
取合い寸法がボクセルに量子化される。実測：1.607 mm ボクセルで 3.50 mm の溝が 3.21 mm になり、
クリアランスが 0.50→0.21 mm に落ちた。Ø5.30 のティアドロップ穴は 6.43 mm の角穴になった。
**トポロジーは正しく、取合いは全部間違っている。** 必ず作り直し、`topopt compare` で証明する。 → spec §17.3

**11. 幾何的な重なりは剛性を予測しない。**
再構築 B は最適形状と 81% 重なっていて、44% しか重なっていない再構築 A より **4倍柔らかかった**。
重なり率は「どこの材料が欠けたか」を見ない。曲げを担うのは中立軸から遠い材料で、
真ん中の材料はほとんど何も担っていない。 → spec §22.1

**12. 骨格は構造の記述として不可逆に情報を落とす。**
中心線＋単一の幅は、変化する断面を失い、コードを設計領域表面ではなく中央軸に置き、
最適化が入れていたブレースを外す。`*_members.scad` は**人が始めるためのスケッチ**であって部品ではない。
これまでの自動再構築はすべて自分の最適解より 5〜7 倍柔らかい。 → spec §17.3

**13. 効かなかった対策を2つ記録しておく。**
`filter_mm` を 4→9 mm にするのは、最適化コンプライアンスを約2倍にした上で再構築はなお 5.8 倍柔らかく、
解決ではなかった。全ノードにガセットを入れるのは 6.7倍 → 5.8倍（13%）で、やる価値はあるが全く足りない。 → spec §22.1

**14. 最適化コンプライアンスと比較してはいけない。**
それは中間密度を含む SIMP の数値で、印刷できない材料の剛性が入っている。
実測でしきい値処理後の中実形状との差は 36%（SIMP 30.6 vs 22.6 N·mm）——悪い再構築を合格に見せるのに十分。 → spec §11.3, §14

## 造形

**15. 最適化の生結果はサポートが要る。手で再構築すると 0 になる。**
実測で生結果 883 mm²（6.1%）に対し、手作りの現行部品は 0 mm²。
オーバーハングフィルタを入れていないので当然だが、
「最適化結果は荷重経路の地図であって部品ではない」の一番わかりやすい証拠。 → spec §13

**16. 平底にすると三つ得をする。**
サポート 0、ベッド接地最大（＝落下に強い）、曲げ引張が層内に乗る。
脚を「細い棒」ではなく「背の高い平底リブ」にする。 → spec §13

**17. 六角ナットざぐりは必ず 30° オーバーハングになる。**
頂点を上げて 45° の尖り屋根にすれば自己支持する（`osmo_tripod.scad` の `nut_pocket()`）。 → spec §13

**18. トポロジー最適化は「細い脚」を否定した。**
最適形状は幅広の三つ葉板＋脚間ウェブ。根元幅を 19→30 mm にしただけで、
質量 +13.5% に対し全ケース改善（最悪ケース +36%）。 → spec §5.2

## はめあい（実物を組もうとして分かったこと）

**22. assert が全部通っても、組めないものは組めない。**
初版は `fit_side = 0.25` の1つのノブで全部のすきまを決めていて、
`.scad` の assert が全部通り、watertight で、サポート 0 mm²、造形性判定も全項目 PASS、
通常荷重の安全率も 6.9〜20.8 あった。
**それでも実物にケースの治具が入らなかった。** assert が見ていたのは
「自部品の中で寸法が矛盾していないか」だけで、**「相手が入るか」は誰も見ていなかった**。
すきまは「守るべき下限」として assert に書く（`case_prong_gap - fin_c_t >= 0.5` 等）。
→ spec §8.1

**23. 4面が同時に空いていないと入らない。オス爪は剛体。**
オス爪は 3.00 mm ×2枚・隙間 3.00 mm の**一体物**なので、メス側は
中央爪の両面と外爪2枚の内面の**4面が同時に**空いている必要がある。
「スロット幅 3.50 に爪 3.00 だから 0.50 空いている」は間違いで、
実際に効くのは**片面 0.25 mm が4か所**。FFF の寸法誤差（内側形状は縮み、
外側形状は太る）が片側 0.15 mm 出るだけで消える量だった。

**24. 中央爪のすきまには幾何的な上限がある。広げると爪が痩せる。**
`fin_c_t = case_prong_gap - 2×fit_centre` なので、中央爪のすきまを広げることと
中央爪を厚く保つことは**同じ材料を取り合っている**。オス隙間 3.00 mm、
6壁 = 2.40 mm を守ると `fit_centre ≤ 0.30` が上限。これは設計判断ではなく算数。
外爪側（`fit_outer`）は台座が外へ伸びるだけで何も痩せないので、そちらは厚く取れる。
**すきまのノブを1つにすると、この非対称性が書けない。**

**25. 「Ø22 まで可」と書いたポケットが Ø21.90 だった。**
`knob_clearance()` はノブ径 `knob_d = 22.0` をそのままポケット半径に使っていた。
すきま 0 なので当然入らない上に、実測すると角の丸めで**Ø21.90 しか空いていない**。
ドキュメントの「Ø22 のノブまで干渉しない」は、印刷誤差以前に CAD の中で既に偽だった。
**「入る相手の寸法」をそのまま「穴の寸法」に代入しない。**

**26. すきまが足りないと、症状は「穴がふさがっている」に見える。**
オス爪先端の逃がし `slot_r` が 0.40 mm しかないと、爪が溝の底で突き当たって
最後まで座らない。するとオス側のピボット穴がメス側の穴より高い位置で止まり、
**外から見ると「ネジ穴の少し外が材料でふさがれている」**ように見える。
穴そのものは正しく開いている。**症状の場所と原因の場所が違う。**

## その他

**19. ヒンジまわりの干渉は解析的に閉じる。**
回転軸まわりに回る相手は、軸からの距離が回転で変わらない。
「自部品の半径 < 相手の最近接距離」を満たせば全角度で干渉しない。
assert 1行で書けて、数値検証より強い。

**20. 落下はエネルギー法では評価できない。**
剛体接触では剛性が支配的になりピーク荷重が発散する。等価減速度（g）で評価し、
「何 g で壊れるか」を答えにする。

**21. `topopt print` の `overhang_pct` はベッド接地面そのものを含む。**
平底の部品でも「24% オーバーハング」と出る。切り分けは `topopt overhang`。 → spec §13.3

**27. ちょうど 45.0 度の面は「サポート要否」の判定を跨いで揺れる。**
`support_area()` の判定は `nz < -sin(45°)` の**厳密不等号**。`util.scad` の
`teardrop()` は屋根が幾何的にちょうど 45.0 度なので、穴径を 5.30 → 5.60 に
変えただけで、同じ形の判定が **0.0 mm² と 40.2 mm²** に割れた。
形が変わったのではなく、浮動小数の丸めがどちらに転んだかの違い。
**閾値ちょうどの面を設計に残さない。** ここでは屋根を 56 度にして閾値から離した。 → spec §13.3

**28. 頂点は「点」で作る。小さな円で作ると天井になる。**
ティアドロップの頂点を `circle(r=0.05)` の hull で作ったら、その下半分が
幅 0.1 mm のほぼ水平な天井として 0.7 mm² 残った。hull の最上部が
1頂点だけになるように作る。

**29. 粗い試し回しの解像度は、一番細い preserve より細かくないと意味がない。**
CLAUDE.md の「まず `--elements 8000` で確かめる」を `gd_mount_study` に掛けたら
voxel 3.67 mm になり、2.40 mm の中央爪が丸ごと消えて
`bolt_tab` 荷重が preserve から外れ、**SETUP INVALID（終了コード 1）**になった。
設定は正しい。粗すぎただけ。**試し回しでも、取合いの最小部材は最低1ボクセルに乗せる。** → spec §15.1

**30. obstacle を広げるとグリッドが変わり、変えていないはずの数字まで動く。**
`clearance_mm` を 0→2.0 にしただけで obstacle の bbox が広がり、
voxel が 1.6065→1.6370 mm に変わって、**設計空間の「ボクセル化体積」が
152,346→142,061 mm³（−6.8 %）**動いた。設計空間 STL は 146,921→146,983 mm³ と不変。
結果、体積差 −6.2 % のうち設計変更の寄与は **−1.0 % だけ**で、残りは全部離散化だった
（voxel を揃えた対照実験 `out/gd_mount_v2grid/` で切り分けた）。
**入力を1つ変えたつもりでも、グリッドは全部の入力の bbox で決まる。**
比較するなら `--voxel` で固定する。 → spec §22.2

**31. 鏡像であるべき2ケースの差が、そのまま数値のノイズ床。**
LC1f / LC1b は X 対称な鏡像荷重なので同じ値になるはずだが、p99.5 安全率は
20.16 / 21.42（v2）、19.24 / 18.33（v3）と 5〜6 % ばらついた。
**この 6 % がその指標の分解能**なので、それ以下の差を改善・悪化として読まない。
対称なケースが揃っているときは、無料で手に入る誤差評価として使う。

**32. 等方で通るテストは、異方性の並び替えを1つも検出しない。**
Voigt のせん断の並びを、本実装は `[xx, yy, zz, **xy, yz, zx**]` にしている
（`hex8.b_matrices` の行 3/4/5 がその順だから）。教科書の `yz, zx, xy` で
テンソル変換を書いたが、**等方 D は3つのせん断対角が全部 mu なので何も起きず**、
PLA / PETG のカードも Gyz = Gzx なので気づけない。
`Gxy=900 / Gyz=600 / Gzx=300` の合成カードを作って初めて赤くなった。
さらに悪いことに、**`build_axis: Z` では回転が単位行列なので、
カード単体を見るテストは並びが逆でも通る**。回転後のせん断対角を見る検査を
足すまで、意図的に壊した実装がテストを素通りした。
**異方性の検査は「3つとも値が違う入力」で、「回転させたあと」に見る。** → spec §11.5

**33. 感度のテストは、式を書き写したら何も検査していない。**
最適化の感度は出力のどこにも出ないので、符号や係数を間違えても
「少し悪い形に収束して、それでも形は出る」だけで失敗が見えない。
テスト側に導関数の式をもう一度書くと、**作者とテスタが同じ思い込みをしたことしか
証明しない**。`objective_and_sensitivity()` をループから関数として切り出し、
**出荷されるその関数を**中心差分で差分するようにした。
penal の因子を落とす変異を入れて、実際に赤くなることを確認している。 → spec §22.1

**34. `.frd` は固定幅。空白で切ると負の値で壊れる。**
CalculiX の結果ファイルを `line.split()` で読むパーサを書いたら、
`0.00000E+00-5.00000E-02` のように**負値が前のフィールドと繋がっている行**で
2つの数字が1トークンになって落ちた。実解析では変位の半分が負なので、
これは例外ではなく常態。**3列＋10列＋12列ずつ**の固定幅で切る。
（幅の違う版のために空白分割はフォールバックとして残す。）

**35. 力の釣合いが通っても、モーメントの釣合いは通らないことがある。**
節点集合を意図より 10 mm ずれて選んでも、**力の総和は完全に釣り合う**。
ずれるのはモーメントだけ。境界条件が意図どおりかを見る検査としては
**モーメント側が本命**で、力の釣合いだけを見ていると
「支持位置を間違えたまま完璧に釣り合っているモデル」を見逃す。 → spec §19.4

**36. 単位を間違えても静解析だけは完全に正しく出ることがある。**
CalculiX の密度を kg/m³ のまま書くと（正しくは tonne/mm³）、
**静解析の変位も応力も 1 桁も狂わない**。密度は静解析に入らないから。
狂うのは座屈係数と固有振動数だけで、しかも 10⁹ 倍。
**「静解析が合っているから単位は正しい」は成り立たない。**

**37. モデルを大きくすると、取合いは解像度から落ちる。**
検証用に3脚のカメラ位置を 15 cm 上げたら、bbox が 8 倍になった。
同じ要素数ならボクセルは 1.64 → 4.0 mm。**カメラ爪の溝 3.80 mm・ボルト穴 Ø5.60 mm は
マス目以下**になり、obstacle として渡すと
「preserve と obstacle が1セルを超えて重なる」で `SETUP INVALID` になった。
2.4 mm を刻むには約1000万要素が要るので、これは解像度を上げて解ける問題ではない。
**取合いは preserve（中実）のまま最適化に触らせず、最後に CAD で作り直す。**
生の最適化結果を部品にしない規則は元から在るが、
**大きいモデルではそれが任意ではなく必須になる。** → spec §5.3

**38. 掃引域の obstacle は、全周の円環で書くと自分の部品を飲み込む。**
カメラの首振り範囲を「ヒンジ軸まわりの円環」として書いたら、
ヒンジより下の台座（preserve）まで丸ごと入って設定エラーになった。
カメラは **±30 度しか振れない**のに、360 度ぶんを禁止していたため。
**掃引域は実際に振れる範囲だけを掃く。**
併せて、掃引域の上端は部品が届きうる高さで切る——切らないと
ボクセルグリッドがカメラ上端（z=238）まで伸び、同じ要素数でマス目が粗くなる。

**39. 背を高くすると、強度より先に転倒が効くようになる。**
背の低い3脚は 30 N 押しても転ばないので、荷重ケースは強度で決まっていた。
カメラを 238 mm に上げると、接地円を Ø104 → Ø300 に広げてなお
**1.08 N で転ぶ**。それより大きい水平荷重を構造ケースとして与えるのは意味がない
（部品は倒れている）。**荷重ケースの大きさは、まず転倒荷重を計算してから決める。**
`.scad` 側に転倒荷重の assert を置いて、寸法を変えたら落ちるようにしてある。

**40. 単位換算を1行にまとめると、1000倍間違えても気づかない。**
静水圧を MPa で出す係数を、頭の中で2段階（mm→m、Pa→MPa）まとめて書いたら
**1000 倍**になった。10 m で 98 MPa。桁が大きすぎるが、
**それが変だと分かるのは書き下したときだけ**で、コードを読んでも変には見えない。
**換算は使う場所で1段階ずつ書き、既知の値（10 m ≒ 1 気圧）をテストに入れる。**

**41. 閉曲面の圧力積分は浮力になる。ただで手に入る検証。**
静水圧の節点荷重を組んだとき、`np.roll` のラップを潰す端を逆に指定していて
**上面と下面が入れ替わり**、さらに圧力を面ではなくボクセル中心の深さで
評価していて**ちょうど 10 % 過小**だった。どちらも符号規約を睨んでも見つからない。
密閉立方体の合力が **ρgV（アルキメデス）に一致するか**を見た瞬間に両方出た。
**閉じた形の合力に理論値があるなら、それを検査にする。**


**42. 設計空間がプリンターより大きければ、最適化の結果は必ず印刷できない。
それは解いた後に分かることではない。**
`tall_tripod` の設計空間を接地円 Ø300 mm で描き、**3.6 時間**かけて最適化を回し、
出てきた STL は 268 × 232 × 184 mm。X1-Carbon の実用範囲は 250 mm 立方なので、
**24 通りのどの向きに置いても入らない**。
最適化は設計空間の中にしか材料を置かないので、
**「入るかどうか」は解く前に確定していた**。誰も見ていなかっただけ。
`topopt print` はこの検査を持っていたが、**STL ができた後にしか動かなかった**。
→ `printers.py` に印刷範囲を一元化し、`designspace.validate()` で
`topopt setup` の段階（数秒）に検査するようにした。判定は二段構え:

- **preserve が入らない** = どの候補形状も入らない（preserve は必ず残るから）→ エラー
- **設計空間が入らない** = 入るかどうかは最適化次第 → 既定でエラー。
  解いた後にしか分からない答えは、数時間かけた後では手遅れなので。
  意図的に分割する部品は `printer.allow_oversize_design_space` で明示的に許可する

**43. 「別の向きなら入る」は合格ではない。**
向きを変えれば入る部品は、**その向きで印刷しなければならない**。
すると層の向きが変わり、`build_axis` に紐づいた直交異方性の材料軸が
実物と食い違う——つまり**さっき回した解析はその物体を記述していない**。
`fits_any_orientation` と `fits_as_declared` を別の値として持ち、
前者だけが真のときは「`build_axis` を宣言し直して回し直せ」と言う。

**44. 印刷範囲・転倒荷重・支柱の高さは、独立に選べない。**
`tall_tripod` を作り直すとき、この三つが一本の線で結ばれていることが分かった。
背を高くする → 転びやすくなる → 接地円を広げる → プレートに載らなくなる。
1 N で転ばない条件（実際に使っている osmo_tripod と同じ安定性）を保つと
`r_foot ≥ (z_hinge + 65)/1.72`、プレートは `2·r_foot ≤ 240`。
**支柱 100 mm には接地円 250 mm ちょうどが要り、余裕がゼロになる。**
当初 100 mm と書いた assert を 85 mm に下げたのは、通すために緩めたのではなく、
**印刷範囲がその三角形を閉じたから**。
`.scad` 側にも印刷範囲の assert を置き、CAD を描いた時点で落ちるようにした。

**45. 最適化の「自由度」を測っておかないと、CAD をなぞっただけの結果を
最適解として発表してしまう。**
トポロジー最適化は、与えられた余地の中でしか答えを出さない。
余地が消える経路は三つあり、**どれも出力を見ても分からない**:
設計空間が preserve の薄い皮でしかない／preserve が最終形状の大半を占める／
荷重と拘束の位置が preserve で固定されている。
三つ目がいちばん見落とされる。**荷重・拘束は preserve の上にしか置けない**規則があるので、
**脚の位置は必ず人間が決めている**。最適化が決めたのは「どう到達するか」だけ。
これは運用として正しいが、**黙っていると読み手は最適化された配置だと思う**。
→ `freedom_report()` が三つとも数値で出し、
`assumptions.md` の「この研究が示していないこと」に自動で載る。

**46. `scipy` の距離変換は、配列の端に接した領域を実際より厚く測る。**
`distance_transform_edt` は配列内のゼロまでの距離しか見ないので、
グリッド境界に接した mask は「向こう側は無限に材料」と扱われる。
2 ボクセル厚のスラブをグリッド端に置いたテストが 4 ボクセルと答えて気づいた。
実運用では `build_setup` が `pad_voxels` で余白を入れているので出ないが、
**手で組んだ Setup でテストを書くときは必ず内側に置く**。

**47. 進捗ログの出力間隔を確かめずに、そこから速度を計算しない。**
`tall_tripod` を 3.0 mm で回し、ログに `iter 1` が出たあと 19 分待っても次が出ないので
**「1反復 19 分、45 反復で 14 時間」と判断して打ち切り**、study を 4.0 mm に粗くした。
**間違いだった。** `topopt opt` は**5反復ごと**にしか行を出さない。
**測ったのは待ち時間であって、反復時間ではない。**
しかも判断を docs と study のコメントに「実測」として書き込んでいた。

**そして訂正のときに同じ誤りを繰り返した。** 手元にあったのは
「5 反復に 19 分**以上**」という**下限**だけなのに、
訂正文には「1 反復 4 分弱・約 3 時間」と**点推定**を書いた。下限から上限は出せない。
きちんとした数字が出たのは、4.0 mm で最後まで完走したあと:
**17,902 セルで 122 秒/反復**。3.0 mm は 43,833 セル（2.45 倍）なので
**約 5 分/反復・40 反復で 3.5〜4 時間**が正しい見積もり。

→ 速度を口にする前に**出力間隔を確認する**（`if it % 5 == 0` の類を読む）。
→ **下限しか無いときは下限として書く。** 「以上」を「約」に書き換えない。
→ 「実測」と書くときは、**何をどう測ったのかを一緒に書く**。
そう書いてあれば、この間違いは書いた時点で自分で気づけた。

**48. フィルタ半径がボクセル 1 個未満なら、フィルタは何も決めていない。**
`filter_mm` 6.0 を 4.0 mm ボクセルで使うと 1.5 ボクセル。
グリッド自体が 2 ボクセルの床を課すので、**最小部材を決めていたのはフィルタではなくマス目**。
出てくる部材は全部きっちり 8.00 mm ＝ 2 ボクセルになり、メッシュ判定に落ちる。
「最も薄い断面に 3 要素以上」を満たしたいなら **`filter_mm` ≥ 3 × voxel** が要る。
代償は鈍さで、細い部材が欲しければマス目を細かくするしかない——そして #47 の値段がつく。
**この二つは同じ一つのトレードオフの両端で、片方だけ見ると必ず間違える。**

**49. 部品全体の統計を、最適化のせいにした。実際は preserve のせいだった。**
`filter_mm` をボクセルの 3.25 倍まで上げれば最薄断面が 3 ボクセルを超える、と踏んだ。
**代表寸法は 2.0 → 4.0 ボクセルに太ったのに、最薄部は 2.0 ボクセルのまま**だった。
そこで「Heaviside 射影の beta が上がると境界がフィルタ半径より細く尖るからだ」と書いた。
**もっともらしいが、間違いだった。**

領域で割って数えたら一発だった（4.0 mm run、距離変換の尾根 443 点）：
**2 ボクセル以下の 169 点はすべて preserve、最適化された材料は 0 点**（p5 13.86 mm）。
射影が原因なら尖るのは最適化された境界のはずで、preserve は CAD が寸法を決めていて
フィルタも射影も触らない。**フィルタは最初から効いていた。**

**ここで大事なのは、射影の説明が「間違い」ではなく「無関係」だったこと。**
後に 80 反復で回し直すと beta 16 での反復が増え、射影は実際に最適化された境界へ
2 ボクセルの点を 4 つ作った。機構としては実在する。
**実在する機構を、実際には起きていない現象の説明に充てていた。**
もっともらしい仮説ほど、数える前に採用されやすい。

→ **部品全体で取った統計を、その一部を作った処理の責任にしない。**
    領域で割って数えてから原因を言う。`min_member_size` は既に `where=free` を持っていて、
    docstring に「2.5 mm のカメラ爪がフィルタ違反として読まれる」と同じ話が書いてある。
    **同じ落とし穴を、道具の中に既に一度見つけて避けてあったのに、読む側で踏んだ。**
→ 副産物として、**マス目を細かくしても直らない**ことも分かった。
    preserve の 2 ボクセル以下の割合は 4.0 mm → 99.8 %、3.0 → 20.6 %、2.0 → 9.2 %、1.5 → 6.6 %。
    p5 が動くには 5 % 未満が要る。**「解像度を上げれば通る」も、測る前は同じ推測でしかなかった。**
known-issues G1。

**50. 並列に回した重い run が、互いを殺す。**
24 コア空いていたので最適化を3本同時に流したが、3本とも
`MemoryError: Unable to allocate 3.94 MiB` で落ちた。**コアではなくメモリが先に尽きた**——
このマシンは Resolve と Chrome 26 プロセスと VS Code で常時 28 GB を使っており、
空きは 3 GB しかなかった。1本なら 200-400 MB で収まる。
→ **並列度はコア数ではなく空きメモリで決める。** 流す前に実際の空きを見る。

**51. パーセンタイルの判定は、母数を太らせるだけで「合格」にできる。**
「最も薄い断面」は尾根の厚みの**下位 5 %**なので、
接地パッドを厚くする（9 → 13 mm）と薄い点は 493 → 25 に落ちた。正しい修正。
そこで欲を出して 16 mm まで上げたら、**薄い点は 25 → 27 と増えたのに判定は合格になった**。
ハブ座が太って尾根の点が 159 → 294 に増え、**分母が薄まっただけ**だった。
→ **パーセンタイルを動かしたときは、分子と分母を別々に見る。**
    比率が下がったのは「悪い点が減った」からとは限らない。
    材料を足せば判定を買えるなら、その判定は材料の量を測っている。
    ここでは 13 mm を採り、16 mm は捨てた。**判定は不合格のままだが、直したのは実在の欠陥のほう。**
known-issues G1。

**52. 「あと少し回せば収束する」を、回さずに言った。倍にしても 1 回も満たさなかった。**
`tall_tripod` が 40 反復で `max_iterations` に当たったので、
「形はほぼ固まっている（灰色度 0.061、形状変化 0.0012）から反復数が足りないだけ」と書いた。
80 反復で回し直したら、**同じ `max_iterations`** で終わった。
4条件のうち**密度変化だけが 80 反復中 0 回しか閾値を満たさず、減少傾向すら無かった**
（0.166 → 0.122 → 0.118）。目的関数は 14 回、体積は 25 回満たしている。

指標は最大値だった——`generative.py:307` は
`change = np.abs(xnew - x)[free].max()` と全自由セルの最大値を取る。
そこで **「#49 と同じだ、数個のセルが振動して最大値を張り付かせているんだ」と書きかけた。**

**数えたら違った。** 自由セル 16,876 のうち、生の設計変数が 0/1 でないものが **1,180（7.0 %）**、
0.1〜0.9 が 651。射影後では 2,503（14.8 %）。**「一握り」ではない。**
形（しきい値を跨ぐセル）は固まっているが、**その下の連続変数は本当に固まっていない**。

→ **「同じ形の欠陥だ」というパターン認識そのものが、#49 と同じ罠だった。**
    #49 で「もっともらしい機構を、数える前に採用した」と書いた直後に、
    **その教訓を使って別のもっともらしい話を作りかけた。**
    構造が似ていることは、原因が同じであることを意味しない。
→ 実務的な帰結: **「最大値だから分位点にすれば通る」と即断しない。**
    7 % のセルが動いているなら、それは指標の欠陥ではなく本当の未収束かもしれない。
    どちらかは**反復ごとに「変化 > 0.01 のセル数」を残さないと分からない**。
    いまの `history[]` はスカラーしか残さず、`optimize()` に warm start が無いので
    **終わったあとからは調べられない。測りたい量は、走っている間に記録するしかない。**
→ 「あと少しで収束しそう」と言う前に、**その指標が実際に下がっているかを見る。**
    形が固まっていることは、その指標が下がることを意味しない。
known-issues G6。

**53. 書き出した形が、解析した形と同じ高さに立っていなかった。**
「最適化した部品の STL が最下層から1,2層浮いている」という報告を受けて測ったら、
**`write_smooth_stl` が全軸で h/2 ずれていた**。marching cubes が返す index k を
「ボクセル k の隅」と読んでいたが、実際には**中心**。`tall_tripod_smooth.stl` は
自分の足より 2 mm 下にあり、**`printcheck` が「プレートに入る」と判定した
bounding box の外に 2.86 mm はみ出していた**。ついでに法線も内向き（＝裏返し）だった。

**7 個の立方体グリッドに 3×3×3 の塊を置くだけで再現した。**
`write_blocky_stl` は [2,5]、`write_smooth_stl` は [1.5,4.5]。
本番の 8,600 三角形の出力に載っていた欠陥が、**27 セルのテストで落ちる**。
同じ形を書き出す関数が3つあって、**同じ枠で書いているかを誰も確かめていなかった**。

さらに、直したつもりで**もう半分残っていた**。
解析した mask の bounding box にクランプすれば「下にはみ出す」は止まる。
**「上に浮く」は止まらない。** preserve に足が含まれていた v3 では
`floor_mask` が押さえていたので気づかなかったが、v4 で足を preserve から外した瞬間、
2 セル幅の足は sigma 1 のガウシアンに丸ごと削られて **4.11 mm 浮いた**。
部品が何も踏んでいない状態で「印刷できます」と出ていた。
→ **`floor_mask` に渡すのは `preserve | (mask & ground)`。**
    スムージングが動かしてはいけないものは2つある——**取合いと、接地面**。
→ **「クランプしたから直った」を、浮く側でも確かめずに言わない。**
    はみ出しと浮きは別の向きの失敗で、片方の対策はもう片方に効かない。

**54. 拘束を自由にしたら、安定性を担保していた唯一のものが消えた。**
`tall_tripod` v3 は接地パッド3つを preserve に置いていた。
「荷重・拘束は preserve の上にしか置けない」ので、**脚の位置は人間が決めていた**。
v4 でそれをやめ、`{"contact": "ground"}` の接地拘束にして「片脚引っ掛け」を
1ケース（+Y の扇形）だけ残したところ、最適化が出したのは
**+Y に傾いた1本柱**だった。接地 2 点、footprint 50 × 140 mm。**見た瞬間に倒れる。**

理由は測るまでもなく明快だった。**接地拘束は両側拘束（glued）なので、
FEA の中で部品は転倒できない。** コンプライアンス最小化は転倒を表現しない。
だから「立っている」ケースはどれも幅を要求せず、細い柱をどこかに1本立てるのが最適になる。
**幅を要求していたのは唯一「片脚引っ掛け」で、それが1方位しか無ければ、
柱をその方位へ寄せれば済んでしまう。**

→ **v3 が三脚に見えていたのは、最適化が安定性を考えたからではない。
    人間が3点を置いたからだった。** 入力を外して初めてそれが分かった。
    **入力を外したときに何が壊れるかが、その入力が本当は何をしていたかを教える。**
→ 対処は「片脚引っ掛け」を 120 度ずつ3ケース。これで初めて三脚が出た
    （接地 5 パッド、footprint 200 × 170 mm）。
    **人間が決めているのは「3方位、だいたいこの辺」だけ**で、半径も接地点の数も脚の形も
    最適化が決めている。v3 の 16 mm パッド固定よりは緩いが、**ゼロではない**。
→ **転倒は剛体の条件で、コンプライアンスでは書けない。** 閉形式で別に見るしかない
    （`tall_tripod.scad` の `tip_force_best_N`）。known-issues G7。

**55. 「実測値・変更禁止」は、出典が無ければ検証できない。**
`tall_tripod.scad` の `case_*` には「実測値なので変更禁止」とだけ書いてあった。
参照 STEP（`osmo-action-6.step`）を解析エンティティで読み直したら**全部合っていた**が、
1つだけ読み違える余地があった: `case_prong_r = 7.50`。
STEP の `CYLINDRICAL_SURFACE` は **r = 7.00** で、これだけ見ると 7.50 は間違いに見える。
実際は**中心が y = ±0.5 にオフセットされている**ので、ヒンジ軸から見た外接半径が 7.50。
**「7.0 に直しました」で 0.5 mm 食い込む改変が入りうる状態だった。**
→ 数字の隣に、**その数字が STEP のどのエンティティから来たか**を書く。
    `assert(case_prong_r >= case_prong_tip + 0.4, "...ENVELOPING radius...")` で
    読み違えを機械にも止めさせた。
→ そのうえで**組み立てを実際にやる**。`topopt clearance` に
    STEP から起こしたケースを渡して ±30 度を5点掃くと、
    **全点で干渉ゼロ・最接近 0.30 mm（＝設計した爪のすきまそのもの）**だった。
    寸法表の照合と、組んでみることは別の証拠。

**56. 「CAD の寸法で戻した」と書いてから、測ったら 0.4 mm 違った。**
`finish` 段（解析結果に CAD の preserve を足し戻し、CAD の穴を引く）を実装して、
docs に**「取合いは CAD の寸法どおりに出る」と5か所書いた**。
出荷ファイルを 0.1 mm で測り直したら:

| | CAD | 出た値 |
|---|---|---|
| 外側の爪 | 4.00 | 4.00 |
| 溝 | 3.80 | **4.00** |
| 中央爪 | 2.40 | **2.00** |
| ボルト穴 | Ø5.60 | Ø5.60 |

**量子化が消えたのではなく、刻みが 10 mm から 0.5 mm に変わっただけ**だった。
しかも誤差は半ボクセルではなく**1ボクセル**——幅は両側の面が独立に丸まるうえ、
cut は外側に丸まる（セル中心が穴に入れば消える）ので、細い方に 2 回効く。
→ **「量子化がひどい」を「量子化が無い」に書き換えていた。**
    改善は本物（10 mm では**存在しない**特徴が 0.5 mm では ±0.5 mm で出る）だが、
    **段違いに良くなったことと、正確になったことは違う。**
→ 対処は数字を出すこと。`feature_tolerance_mm` を返り値に入れ、
    `PRINT.md` と docs は図面値ではなくその許容差を引用する。
→ **実装した本人がいちばん確かめにくい。** 自分の頭の中では「CAD を足して穴を引く」
    という**手続きが正しい**ので、出てくる寸法も正しいはずだ、と思ってしまう。
    **手続きの正しさは寸法の正しさではない。測る。**

**57. 通っている assert が、何も守っていなかった。**
`tall_tripod.scad` には `assert(bore_roof_deg >= 50)` があり、
「ボルト穴の天井が 56 度なのでサポート不要」と読める。**通っていた。**
ところが穴の向きを測ったら、ティアドロップの頂点が**横（+Y）を向いていた**。
`rotate([0,90,0])` だけでは押し出し軸は +X で合うが、2D 図形の +Y はグローバルの
+Y に残る。**頂点が上を向いていないので、穴の天井は水平のまま**だった。
assert は「頂点が上を向いていれば 56 度」という**定数の計算**をしていただけで、
向きは一度も見ていない。ナットの尖り屋根も同じ向きに倒れていた。

出荷している `osmo_tripod.scad` には `rotate([90,0,0]) rotate([0,90,0])` と
**合成が入っていて、コメントに「軸を +X、頂点を +Z に向ける」と書いてある**。
検証モデルを作るときに片方だけ写して、コメントは写さなかった。
→ **パラメータから計算しただけの assert は、そのパラメータが使われる向きを検査しない。**
    形の性質を主張する assert は、**形を測って**確かめる
    （ここでは finished STL をボクセル化して Z 方向の張り出しを見た：
    中心から上に 5.00、下に 2.80 ＝ 頂点が上）。
→ **コピー元のコメントは、コピーする理由が書いてある場所。** 落とさない。

**58. 遅かったのは要素数ではなく、反復数だった。**
`runtime.py` はずっと前から「セルあたりコストが study によって2倍以上ばらつく」と
言っていた（`tall_tripod` 16.5 s/反復/ケース、`gd_mount` 9.3）。**誰もそれを深追いしなかった。**
4 mm の tall_tripod を実際に最適化した密度場（0/1 に近い二値）で解くと、
Jacobi 前処理付き CG は1ケースあたり **12,044 反復**かかっていた。要素数は 101,808 と
そこまで大きくない。**遅さを決めていたのは条件数（反復回数）で、要素数ではなかった。**
幾何マルチグリッド前処理（格子を2×2×2ずつ粗くして解く）に替えると、同じ答え
（コンプライアンス相対差 1e-6 以下）に **74 反復**で届く。GPU はそれとは別に
1反復あたりの計算をさらに約30倍安くする。

対策として実装する前に、他の道も測って捨てた: 疎行列を組んで CPU で解く
（1回のマット・ベクトル積は 30 ms で行列を持たない方式の 45 ms より速いが、
組み立てに 1〜2 秒・0.3 GB を払う価値が無い）、スレッド並列のマット・ベクトル積
（せいぜい 1.4 倍）、pyamg の代数マルチグリッド（190 反復まで減るが、
その前処理自体の1反復が 0.5 秒かかり、結局91秒/解と遅い）。

→ **大きいグリッド予算を買う前に `cg_iterations` を読む。** 遅いのが反復回数のせいなら、
   要素を減らしても直らない。
→ **前処理は物理ではない。** 新しい解き方を既定にする前に、旧い解き方（この場合
   `--solver cpu:jacobi`）と同じ答えが出ることをテストで示す（`tests/test_solver.py`）。
→ **測った代替案は、採らなかったものも書き残す。** 数字を残さないと、
   次の人が同じものを測り直す。 → spec Phase 10, known-issues G4/G9

**59. 感度が厳密に 0 のセルで、符号を比較していた。**
感度の中心差分テストは、全ノードが固定されたセル（解析的な感度が厳密に 0）で
`np.sign(fd)` と `np.sign(analytic)` を比べていた。CPU の直接解ではたまたま
両方とも厳密に 0 が返っていたので気づかなかったが、GPU の Cholesky 分解に替えた途端、
片方が **-1.7e-11** を返し、符号が食い違ってテストが落ちた。**ソルバは正しい**——
浮動小数の丸めの範囲で、意味の無い符号を比べていただけ。
→ **符号のテストにはスケールが要る。** 両方の値が最大感度の 1e-8 未満なら、
   その比較は飛ばすか絶対許容差（atol）で見る。 → spec §22.1

**60. 密度フィルタの転置が転置になっていなかった。**

それまで気づかれなかった——AM フィルタの実装で密度チェーン全体を中心差分で

→ 密度チェーンの演算子は、実装するたびに中心差分に対する随伴テストを付ける。

**61. プレートは配列の端ではない。**
tall_tripod のグリッドは設計空間の下 20 mm から始まるので、配列の index 0 を

→ 層ごとのルールは、プレートを常に `ground_mask` / 設計空間から取る。配列の index 0 からは取らない。
   テストは、プレートの下に空の層があるグリッドで書く。

**62. 「浮かない」保証は smooth max の中立点と射影しきい値を揃えることから来る。**
補正していない p-norm smooth max は層ごとに 4 % 成長するので、5 支持の一様な密度場が
プレートの上では読み取り値 0.45 でも 4 層上では 0.5、8 層上では 0.6 と読まれ、
射影がその上のほうだけを残してプレートを落とした——印刷物はベッドから 16 mm 浮き、接地面積 0 mm²。
補正して中立点を 0.5（＝射影しきい値 eta）に置いたら直った。代償は 0.5 未満の一様場が
層ごとに減衰すること（volfrac 0.04 で 14 %/層）で、最初の 1/3 反復で 0→1 に混ぜ込む（`ramp`）
という値段を払っている。さらに smooth min は真の最小より最大 0.005 高いという帯を持つので、
1〜2 ボクセルが支持なしのまましきい値をすり抜ける——これは `prune_unsupported` で刈って数を記録する。
→ 平滑近似がしきい値に食わせられるときは、平均誤差ではなく**しきい値における不等号の向き**を検査する。

**63. OC は 0/0 を「消せ」と読む。**
目的関数・体積の両感度がともに厳密に 0 のセルは、更新式が特に何も指定しないので、
移動制限のぶんだけ毎反復下方向へ動かされ、上から場が抜けていった。

→ 死んだセルは据え置き、移動制限は beta に合わせて絞り、収束を宣言するときは

**64. MMA の弾性スラックは、目的関数がオーダー1のときしか制約として効かない。**
正規化コンプライアンス目的は荷重ケース数から始まり、100×4×4 の試験片で
7×10⁶ まで育つ。MMA の弾性スラック（制約違反1単位あたり重み1000）は
目的関数の勾配がオーダー1でないと拘束を締められない。実測：目的関数を毎反復1へ

再スケールすると 0.400 に戻る。
→ MMA を使う対数スケールの制約付き最適化では、目的関数自体のスケールを
   毎反復合わせる。「制約が緩い」に見える不具合の実体が目的関数のスケールのことがある。
   → spec §11.6、Phase 12

**65. 実行不可能な強度要求は、最適化を止めない。もう一方の制約を犠牲にする。**

SF ≈ 6.9 しか出ない設定）にしたところ、最適化は停止も例外もせず、
**体積を volfrac 0.3 → 0.419 まで増やして**それでも SF×FI 1.60（中実解析で SF 3.78）で終わった。

同時に緩め、どちらも守れないところで妥協する。
→ 応力制約つきの run では、**応力の行だけでなく体積の行も必ず読む。**
   体積が volfrac から動いていたら、それは「その要求はその体積では無理だった」という
   実行不可能性の症状であって、バグではない。 → spec §11.6・§19.2、Phase 12

**66. 粗格子の密 Cholesky は、荷重の周りの密度が完全に失われると分解に失敗する。**
応力制約つきの試し回しで、主解のマルチグリッド階層を組む途中に torch の Cholesky が
「正定値でない」で落ちた。密度場が 0 に近い（`E_min` = 1e-9·E）領域に荷重や拘束が
乗ると粗格子作用素が特異に近づく。制約側の問題ではなく、密度場が極端になれば
どの run でも起こりうる（torch の Cholesky は numpy より厳しい）。**中止する代わりに、対角を `(1e-10, 1e-8, 1e-6, 1e-4, 1e-2) ×
最大対角` の最小のシフトで分解できるまでずらす**（`coarse_shift` として記録）。
前処理は物理ではないので、これをしても細格子の CG は同じ許容誤差まで解いており、
答えは変わらない。
→ 前処理が特異に近い場面は「解けない」ではなく「前処理を緩める」で対処できる。
   ただし**前処理を緩めたことは記録に残す**（`coarse_shift` を見れば分かる）。
   → spec §11.6、architecture.md multigrid.py、Phase 12

**84. GPU が遅いのではなく、Python のスカラーが GPU を止めていた。**

**86. 体積制約の二分探索が最適化時間の 1/4 を使っていた。**
自己支持拘束つきの OC は体積を「フィルタ → AM 掃引 → 射影」の後で測る（厳密体積）。
その二分探索が毎反復 [1e-12, 1e12] から始まり、1 反復あたり 17 回の `vol_of`
（各 75 ms の AM 掃引を含む）を呼んでいた——1.45 s/反復、ソルバの次に大きかった。
乗数は反復間でほとんど動かないので、前反復の値の ±64 倍から括り、区間内は Illinois 法
（修正 regula falsi）で詰める。停止条件（目標体積の 1e-4）は変えていない。
**ループの中の「毎回ゼロから探す」は、探索対象が前回とほぼ同じなら必ず疑う。**
AM 掃引そのものは層ごとに J 項をまとめて計算するよう書き直したが速くならなかった
（numpy の演算回数ではなく配列の走査量で決まっていた。整数べき乗の反復二乗も同様）——
**測ってから「Python のオーバーヘッド」と言うこと。**
→ `generative._oc`、`amfilter.AMFilter.forward`

**87. GPU の float64 は「行列積」で払っていた。**
要素ごとの積 `(nel·m, 24) @ (24, 24)` が matvec の 2/3（50k 要素・右辺 3 本で 1.5 ms / 2.4 ms）。
gather / scatter の atomics ではなかった（0.17 + 0.23 ms）。float32 なら 0.23 ms。
前処理（V サイクル）は「K⁻¹ に近い作用素」であればよく答えを決めるのは外側の CG なので、
**V サイクルだけ float32、粗格子の Cholesky と CG は float64** にした。float32 の前処理は
反復ごとに厳密には同じ作用素でないので CG は flexible 形（β に Polak–Ribière）。
uniform 密度で 7.9 s → 3.9 s、答えはコンプライアンス相対差 1e-10。
**精度を落とすなら、落とした場所の誤差が最終的にどこで拾われるかを言えること**——
ここでは float64 の残差ノルムが拾う。
→ `multigrid.MGPreconditioner(mixed=True)`、`solve.pcg_block(flexible=True)`、
`tests/test_solver.py::test_mixed_precision_cycle_matches_float64`

`iters//8` ごと、beta は `iters//5` ごと、自己支持の ramp は `iters` の 1/3）は反復数の上に

（volfrac 0.052）は 80 反復の記録では 31〜37 反復目で目的関数が 1e3〜1e5 に跳ね（構造が
切れかけた）38 反復目で戻ったが、40 反復では 21 反復目に跳ねたまま戻らず、**最終形が
NOT CONNECTED** で終わった（23 分かけて）。同時に分かったこと：この study は跳ねている間

**91. セルを 1 に固定しても「面」は固定されない。CAD の取合いが 0.34 mm 外へ動いて、ネジが締まらなくなった。**
#90 で入れた finish 段の平滑化は、ガウスを**すでに CAD ボディを含んだマスク**にかけ、
そのあと CAD のセルを 1 に書き戻していた。これで守れるのは「CAD が**削られない**」ことだけで、
**CAD が外へ**動くことは何も止めていない——頭部は自分自身をぼかして、等値面は CAD 面より
外側に出る。tall_tripod v5 の出荷 STL で実測（解析 3 mm・finish 1.0 mm・σ 1.50 mm）：
ナット側の爪の外面が **11.00 → 11.34 mm**、CAD 頭部のうち **322 mm³ が丸められて消失**。

**膜**として残った——出荷 STL の口 3,228 本のうち 758 本が塞がっており、ナットが入らない。

直し方：**ガウスは最適化した材料にだけかけ、CAD は自分の占有率（occupancy）として合流させる。**

合わせてあるので、体積一致で選んだしきい値 `level` に `+ (level - 0.5)` で載せ替えれば、
**どのしきい値でも等値面は CAD 面に乗る**。cut も同じ扱いにすると穴が丸めで太らない。
実測（v6）：爪の外面は CAD と 0.06 mm 差、幅は 4.00 / 2.00 / 7.00 と図面どおり、ポケットは
3,228 本すべて開通。**「保持している」と書くときは、セルではなく面で測って確かめること。**

**94. 「滑らかにする」の残り3つ：底面・接合部・出力の丸め。**
#93 で瘤を消したあと、利用者から3点。**「底面がスムーズ化されていない」「部品と最適化部品の
接続が浮いている」「接続する箇所だけスムーズにしてつなげないか」。** 3つとも別々の原因だった。

**(1) 接地面を「セルごとに 1 で固定」していたのは、階段を固定していた。** 接地層を固定するのは
脚を浮かせないためで、規約にもそう書いてある（#90 以前の実測で 4.11 mm 浮いた）。だが固定して
いたのは**解析グリッドの footprint そのもの**で、上の本体だけが丸められる。結果は
**「滑らかなドームが、1 セル厚のギザギザのスカートの上に立っている」**形。
正しいのは、**接地面は材料の終わりではなく切断面**だと扱うこと——プレートの下に材料を
**鏡像**して畳み込みを対称にすれば、断面は削れも太りもせず、輪郭は上の本体と同じに丸まり、
浮きもしない。畳み込んだあとプレート下は捨てる。グリッドがプレートちょうどから始まる場合が
あるので、下のセルに書き込むのではなく**パディングで**鏡像を作る。

**(2) CAD をぼかしから外すと、今度は接合部が痩せる。** #91 で CAD をガウスから外したのは
正しいが、最適化材料**自身**のぼけは CAD 面に近づくほど落ちるので、支柱は着地の直前で
細り、取合いは一回り小さい切り株の上に載る。直し方は「**接合部だけ**両方のボディを含む
ぼかしに寄せる」こと。重みは最適化材料自身のぼけ値（自分の表面で 1、1σ で約 1/3、2σ で 0）
にした——距離変換が要らず、連続で、まさに「接続する箇所だけ」になる。

**(3) それでも浮く。`attach` の非接触殻を誰も埋めないから。** `attach` は繋いでよい面以外に
1 ボクセルの殻を張る。**取合いが土台より広ければ、その差分は必ず宙に浮く。**
実測：tall_tripod の台座は 30 × 30 mm、attach 面は 18 × 18 mm、その外側は**全周 2.00 mm の隙間**。
解析の欠陥ではなく study が要求したとおりの形で、それでも部品としては失格（サポート必須、
見た目は破断）。だから**フィレットは非接触殻の中にだけ入ってよい**ことにした
（`bridge_mm`、既定 = 解析ボクセル1つ = 殻の厚みそのもの）。**利用者が宣言した obstacle には
入らない**——ノブを回す空間を finish 段が埋めてよい道理はない。さらに**`cut` の周りにも
入らない**：フィレットは CAD 面の**外**に足す材料なので、公称面ちょうどで終わる穴は
それに塞がれる（#91 の膜が別経路で戻ってくる）。

**(4) 出力の丸めで、閉じているはずの殻に 3 本の穴が開いていた。** STL は三角形ごとに角を
**float32** で持つ。100 mm 付近の float32 の刻みは約 8e-6 mm なので、marching cubes が
同じ点として計算した角が、float64 の最下位ビット違いで**別の float32 に落ちる**。
実測：44.4 万辺のうち 3 本が相手を失い、殻検査は不合格、`topopt ccx` はメッシュを切れない。
**書き出す前にセルの 1e-4（1 mm グリッドで 0.1 µm）に量子化**し、角が一致してしまった
三角形を捨てる。**「検査の公差を緩める」は答えではない**——ファイルの側を正規化する。
→ `finish.blur_across_plate` / `smooth_field(union=, ground=, no_blend=)` / `bridge_mm`、
`meshout.write_smooth_stl`、`test_finish.py` の
`test_the_first_layer_keeps_the_smoothed_outline` /

**95. 接合部のブレンドに境界を付けていなかったので、部品が「座布団の上に載った」。**
#94 で入れた「接合部だけ両方のボディを含むぼかしに寄せる」は、**重みだけで場所を決めていた**
（重み＝最適化材料自身のぼけ値）。その重みは最適化材料のある所ならどこでも約 1 なので、
**取合いの周囲 2σ の全方向**でぼかしが効き、CAD ボディの周りに**ぐるりと襟**が育つ。
出てきた形は、台座の下に**取合いよりも支柱よりも太い枕**があり、その上に部品が載っている——
利用者の言葉で「**部品の下にクッションがついていて、それと最適化部分がくっついている感じ**」。
**滑らかにはなっている。効かせる場所が間違っていた。**

直し方は、ブレンドを**両方のボディから `bridge_mm` 以内**のセルに限ること
（`dilate(CAD, rb) & dilate(最適化材料, rb)`）。これがまさに「両者が出会う入隅」で、
それ以外では CAD の占有率がそのまま立つ。襟は最大でも `bridge_mm` の厚みになり、
支柱より外へは出られない。実測（tall_tripod・3 mm 解析・σ 3 mm・`bridge_mm` 3 mm）：
枕は消え、台座の下の隙間は 0 のまま、取合いの寸法も接地面も変わらず、
三角形は 148,062 → 146,358。

**教訓：** 「どこに効かせるか」を重みの減衰まかせにしない。**効かせてよい領域を集合として書く。**
減衰は連続にするための道具であって、範囲を決める道具ではない。
生の最適化結果（`*_raw.stl`）と並べて描けば一目で分かった——**加工の結果を疑うときは、
加工前と並べる。**
→ `finish.build_part`（`blend_zone`）、`smooth_field(blend_zone=)`、
`test_finish.py::test_the_joint_is_filleted_rather_than_necked`（襟の到達範囲を検査）

**96. 「出荷 STL の上半分が無い」——finish グリッドが解析ドメインそのものだった。**
tall_tripod v7 で、カメラの取合いを子機用の DJI Osmo Action 6 マウント
（104 × 79.45 × **84.5 mm**）に差し替えた。設計空間は高さ 146 mm、パディング込みの
解析ドメインは z = −6..156。取合いを z_hinge に合わせて置くと**先端は z = 196.5** になる。
`finish.build_part` は `shape = mask.shape * f`・`origin` そのままで細グリッドを作っていたので、
`voxelize_stl(..., shape=shape)` は**壁の外を黙って捨てる**。出荷 STL は z = 156 でぶつ切りになり、
**警告も、統計上の異常も、何も出ない**（体積は「足した量」として報告されるので、
足りない量はどこにも現れない）。

**なぜ気付きにくいか。** 「最適化した本体は、解いたドメインの外には存在し得ない」は正しい。
だから細グリッドを解析ドメインに固定するのは、**本体については**正しかった。
`add` / `cut` は CAD で、その規則の外にある——**取合う相手が設計空間に収まる保証は無い。**

直し方は `finish.cover_pad`：`add` と `cut` の bbox を見て、**解析ボクセル単位で**グリッドを広げる
（端数で広げると `_up()` の細セル境界が粗セル境界とずれ、再サンプルした本体が
「解析した形を半セルずらしたもの」になる。それはこの段が下流にいるバグそのもの）。
壁に**触れるだけ**のボディは対象外——従来の結果をビット単位で変えないため。
壁を**越える**ボディには、越えたぶん＋空セル1つを足す（等値面が閉じる相手が要る）。
実測：+Z に 15 ボクセル伸びて 84×84×69、`added_mm3` 143,504 / CAD 実体積 144,200。
`info.grid_grown_voxels` が 0 でない run は、**FEA が一度も見ていない mm を出荷している**
という宣言でもある。

**教訓：** 「解析の格子」と「出荷の格子」を同じものだと思わない。
**入力の一部（CAD）が、解いた空間の外に出ることがある。**
